What this is

The module's substance, reorganised and written from scratch. Same decisions, same tables, same failure cases, in a fraction of the reading. Where the course spends a screen building up to a rule, this states the rule and shows you where it bites.

The module has one spine, and it is worth naming before anything else. Four decisions come before you build: what work Claude owns, what shape that work takes, which reference architecture it fits, and which model and context strategy keep it accurate and affordable. Getting them out of order is the reliable path to an expensive pivot.

1Four properties you design around

Start here, because it explains why every later answer is what it is. Four properties of the model shape everything downstream. None are defects awaiting a fix. They are material properties, the way a structural engineer designs around what steel does.

The trap in each is the same: the characteristic that makes Claude capable in one situation is what makes it fail in another.

Property, consequence, mitigation
PropertyWhat it means for your designThe mitigation
Non-determinism The same input can produce different output across runs. You cannot certify behaviour you observed once Evaluation frameworks. A demo running clean five times is not evidence of determinism
Context as a finite resource The window is a hard edge with a fixed token budget. What goes in, in what order, and what is left out are design decisions affecting both capability and cost Deliberate context strategy, covered in section 6
Confidence is not validity A wrong answer arrives in the same fluent, assured tone as a right one Human-in-the-loop placement and verification, as architecture rather than afterthought
Knowledge and capability boundaries Reliable on topics that are common, recent and consistent in training data. Unreliable on rare, private or fast-changing ones Retrieval, tools, MCP, web search. Make an external system the source of truth instead of the model

The module's own failure case is worth carrying: a team watched a demo run cleanly five times, concluded the behaviour was deterministic, and shipped a financial reconciliation pipeline with no checks around model output. In week two the same statement reprocessed to a different categorisation. Nothing had changed in the input. An analyst found it by accident.

The line to carry

The four properties are present whether your architecture acknowledges them or not. A system that ignores them does not throw an error. It drifts quietly, and the gap is found in an audit or by an angry user, never by the system itself.

A team demos a document classifier to a steering group. It runs correctly on the same twelve sample documents four times in a row. The sponsor asks whether they can now skip building an evaluation set, since the behaviour is clearly stable.

What is the right response?

  1. Agree once the sample size is raised to a hundred documents.
  2. Refuse, because repeated observation cannot certify a system that is non-deterministic.
  3. Agree provided the temperature setting is first lowered to exactly zero.
  4. Agree if production logging captures every single classification for later review.
This is non-determinism misread as stability, and it is the module's own worked failure. The eval set is not bureaucracy, it is the only instrument that can make a claim about behaviour you cannot observe exhaustively.

2Three layers, seven primitives

Two vocabularies, both of which the exam expects you to keep straight. Muddled architecture conversations almost always trace back to collapsing one of them.

The three layers

These are not alternatives. Every deployment involves all three, and each is a different conversation with a different stakeholder.

LayerWhat it isChosen forExamples
Entry pointWhat a person or system interacts with. The wrapper deciding who can talk to Claude and howThe user and the workClaude.ai, Claude Code, a custom app on the API
Build-time interfaceHow an engineer programs against Claude. The layer your code is written toThe engineering team and the integrationDirect API, SDKs, MCP, Agent SDK
Delivery routeWhere API traffic terminates, and so whose infrastructure runs itCloud commitments and compliance postureAnthropic direct, Bedrock, Vertex, Foundry

A decision in one layer rarely dictates the others. The module's failure case: a retail banking proposal put Claude Code in front of branch staff because "it's all Claude". True at the model level, false at the wrapper level, and collapsing the layers erased the distinction that should have ruled it out on sight.

The seven primitives

Every pattern later in the module is an assembly of these. Learn them as one job each.

PrimitiveJobWhat it is
ToolsActA function the model can call to take an action or fetch a result from your code
MCPConnectA protocol exposing a set of tools so multiple Claude clients reach the same entry points
SubagentsIsolate, paralleliseHand a scoped sub-task to a separate context, for isolation or concurrency
HooksGuaranteeDeterministic code firing on defined events to enforce a rule the model cannot skip
SkillsPackage a procedureA versioned, reusable unit of instructions plus optional scripts
Agent TeamsCoordinate peersMultiple agents as peers, each owning part of a larger goal
Dynamic WorkflowsCompose at runtimeAssemble workflow steps at runtime rather than fixing them in advance
Why the inventory matters. The module's failure case is a design review where someone said "we'll use an agent" and five people heard five different architectures. Twenty minutes lost before anyone noticed. The primitives are the shared vocabulary that makes the later patterns compositions of parts you already named.

3Decomposition: the move before architecture

Every solution has three owners, and assigning them early is the whole game. Architects who collapse all three into "what Claude does" produce systems that are slower, more expensive and harder to debug.

OwnerWhat belongs there
ClaudeWork benefiting from language understanding, summarisation, planning, drafting, or tool-mediated action
Existing systemsAnything the partner already paid to make reliable: the order-status service, the policy engine, the rules table, the database of record
HumansJudgement calls, exception paths, approvals, and any moment where being right matters more than being fast

For each piece, decide not whether Claude can do it but whether Claude should own it. Three tests:

  • Reversibility. Can a wrong call be undone?
  • Stakes. What does a wrong call cost?
  • Accountability. Who must answer for it?
The framing shift the module is building toward

Stop asking "where can Claude help?" Ask "where do the four properties argue for Claude over the system that already does this right?" That reframing is the single most portable idea in Module 1.

The worked example is a claims triage assistant that reads a claim, decides priority, looks up policy coverage, and emails the adjuster. Four steps, and only one and a half belong to Claude:

StepOwnerWhy
Read the claimClaudePattern-rich language work, and a constrained output schema puts steerability on your side
Decide priorityExisting systemLooks like a language task, is not. Priority is a deterministic rule living in the partner's rule engine, not in training data
Look up coverageExisting systemSame problem, higher stakes. Coverage tables change and the model cannot know when its version went stale
Email the adjusterSplitDrafting is Claude. Sending is the email system. Above a value threshold, a human approves

A logistics partner wants an assistant that answers driver questions. One frequent question is "what is the current status of shipment 88214?" The team proposes indexing the shipment database nightly into a vector store so the assistant can answer from retrieval.

What is wrong with the proposal?

  1. The chunking strategy was never matched to the structure of these records.
  2. The nightly refresh interval is too long and should instead run hourly.
  3. Shipment status is live state, so it needs a tool call instead.
  4. The embedding model is not tuned for these short structured identifier records.
The module names this the most common reference architecture mistake: retrieval applied to live state. The symptoms are stale chunks, answers that shift with each index refresh, and results contradicting the database. Any scenario about status, balance, inventory or availability is testing this.

4Pattern selection

Three patterns, positioned on two axes: how predictable the path is, and how much autonomy you hand the model.

PatternWhere control flow livesUse when
Augmented LLMNowhere, it is one bounded callTask is well defined, output is verifiable, no reason to split the work
WorkflowYour codeError cost is real, observability matters, steps can be determined in advance
AgentInside the modelThe path cannot be enumerated in advance, and an inconsistent output is acceptable and recoverable

Agents in production are bound by constrained tool entry points, per-turn budgets, explicit permissions and stopping criteria. The module is blunt that these are not options: they are what keeps an agent from becoming a liability.

Four workflow sub-patterns

Sub-patternShapeEarns its place when
ChainingStep 2 consumes step 1's output, linearClean stage handoffs: extract, then classify, then summarise
RoutingA classifier picks the downstream pathInputs vary in kind and each kind needs different handling
ParallelisationConcurrent calls, results aggregated or votedSub-tasks are independent, so sequencing buys nothing
Evaluator-optimizerGenerate, grade, revise, loop to a criterion or retry limitQuality is verifiable but one attempt is not reliable enough

The five-factor decision, in sequence

Walk the factors in order. For each, ask which patterns it rules out. The first factor that rules a pattern out is the deciding one.

FactorAugmented LLMWorkflowAgent
PredictabilityLow, single bounded taskLow, you wrote the pathHigh, unpredictable by design
Error costMedium, no step-level guardsLow, deterministic guards between stepsHigh, full output distribution across turns
ObservabilityMedium, easy to log, opaque insideLow, logs like codeHigh, trajectory reads as a transcript and tooling rarely alerts on it
Latency budgetLow, fastestMedium, predictable but additiveHigh, open ended, budget the worst case
CostLow, fewest tokensMedium, scales with stepsHigh, iterative reasoning and growing context
A correction worth absorbing. The module is explicit that agents are not automatically more expensive than workflows. What drives cost is context accumulation and call count. A badly designed workflow can cost more than a well-designed agent. Design beats the pattern label.

Before you reach for fine-tuning

The instinct when prompting feels unreliable is to fine-tune. On Claude that is usually wrong. The sequence: optimise the prompt, then add tools or retrieval, then move to a stronger pattern such as evaluator-optimizer, and only then consider fine-tuning. Fine-tuning fits very high volume where inference cost binds, latency-critical work where a smaller specialised model wins, or a stubborn output-format problem. Outside those it locks you to a model version for little return. Note that fine-tuning Claude is not broadly available.

A healthcare claims processor handles three document types through fixed, well-understood steps. Regulators require the operations team to reconstruct why any given claim was decided the way it was. Volume is high and per-claim cost is under scrutiny.

Which factor decides the pattern here, and what does it decide?

  1. Cost, which rules out the agent and selects one augmented call.
  2. Observability, which rules out the agent and selects a structured workflow.
  3. Predictability, which rules out the agent and selects a structured workflow.
  4. Latency, which rules out the workflow and selects one augmented call.
Several factors point the same way here, which is common. The exam wants the tightest one. "Reconstruct why any claim was decided" is a hard regulatory requirement, and an agent's trajectory is exactly what current tooling cannot alert on.

5Multi-agent and orchestration

Two roles. The orchestrator owns the goal: it decomposes, delegates and synthesises, and never does the sub-task work itself. Subagents own scoped sub-tasks, each in its own context.

Three things must be designed rather than assumed: how work is decomposed, how each result is structured so it can be combined, and how the orchestrator resolves conflicts and gaps.

The common shape is fan-out: a work item too large for one context, such as a 400-file audit or a 200-document corpus, split into independent units, one subagent each, then synthesised.

The recovery asymmetry

FailureRecoverable?Design response
Subagent returns malformed or empty resultYesValidate each result, retry or re-route, record the gap rather than failing the run
Two subagents conflictYesGive the orchestrator an explicit conflict rule, or escalate to a human
Orchestrator loses the goal or synthesis stateOften notProtect orchestrator state, checkpoint so a failed run resumes rather than restarts
Traces fragment across agentsCross-cuttingPropagate a shared trace identifier so one run is reconstructable end to end
The dangerous failure

The silent one. A subagent drops a unit and the orchestrator synthesises a confident, complete-looking answer over incomplete work. Validate coverage, do not assume it. Fan-out needs completeness accounting or nothing reports the missing piece.

6Reference architectures

References, not blueprints. Understand them well enough to generalise, adapt the shape that fits, and recognise when a workload draws on more than one.

ArchitectureGood looks likeWhere projects go wrong
AgentModel works toward a goal choosing tools and order, autonomy checked by limited tools and a turn budgetUnbounded autonomy: state-changing tools, no review, no turn limit, no measure of goal completion
RAGA stable corpus chunked and indexed, relevant chunks retrieved as contextAnswering about live state. The index is a snapshot
Document pipeline (evaluator-optimizer)Structured extraction against a schema, validated, exceptions routedNo exception path, so low-confidence extractions flow through as if clean
Ticket triage (routing)Classify intent, then route to retrieval, a transactional API, or a human approval layerRetrieval for live order status, no human escalation path, jumping to an agent before measuring the routed workflow
Coding agentAgentic investigation, then deterministic edit, test and review stepsCommits without a human gate, no regression tracking per language or framework, treating it as a conversation rather than a pipeline

Combining two architectures roughly doubles the surface area you maintain, and each carries its own eval contract, so you need separate eval sets per architecture rather than one for the composed system. Reach for a second pattern when two parts of the problem break in genuinely different ways. If you are reaching for a second because you have not decided what problem you are solving, that is a deferred decision, not an applied pattern.

7RAG pipeline design

Chunking is chosen by what the corpus is. Indexing is chosen by how queries are phrased. Those are two separate decisions.

ChunkingEarns its place when
Fixed-size (uniform spans with overlap)Homogeneous unstructured text with weak natural boundaries. Simplest to operate
Semantic (meaning boundaries)Prose where a retrieved chunk must stand alone to answer well
Hierarchical (preserve document structure)Contracts, manuals, policies, where section context carries meaning
IndexingMatchesEarns its place when
Dense (embeddings)Semantic similarityQueries phrased differently from the source: paraphrase, intent, concept
Sparse (keyword, BM25)Exact termsQueries hinging on specific tokens: part numbers, statute citations, error codes
HybridBoth, combinedMixed query patterns, the common production case

When hybrid returns two ranked lists they must be merged, and reciprocal rank fusion is the standard low-tuning default: score each result by its rank in each list, favouring items ranking well in both. For an architect the point is that combining dense and sparse has a known, defensible answer.

Every retrieval design trades among retrieval quality, latency and maintenance. Smaller chunks and hybrid indexing raise quality and latency together. Larger chunks and dense-only lower latency and maintenance but miss exact matches. There is no universal right point, only one you can defend for this corpus and these queries.

8Model and context strategy

Four terms that get conflated, and conflating them produces architecture mistakes:

  • Context window. The model's active attention space. Outside it, nothing exists to the model. Resets between calls unless your application manages continuity
  • Retrieval. External knowledge fetched at query time. It augments the window, it does not replace it
  • Persistent application state. Owned by your system. Order status, balances. Reachable only by tool call
  • Summaries and memory layers. Application-managed continuity. The model has no native memory between calls. This is an architectural choice, not a model capability

Model selection

Sonnet is the default starting point. Move up to Opus only when an eval set says Sonnet misses your quality bar. Move down to Haiku only when an eval set confirms the tradeoff is acceptable. Measured, never reflexive.

The working-memory cliff

Working memory has the hardest edge of the four properties: things work until they do not, and the transition is abrupt. Do not budget the full window. Budget the largest realistic conversation, plus retrieved context, plus system prompt, plus scratch, plus margin. The window is a ceiling, not a target, and designing toward the ceiling means hitting it in production. Measure token counts from the API usage field rather than estimating from characters.

Four context strategies

StrategyEarns its placeBreaks down when
MonolithicBounded tasks with predictable input, stable prefixes that benefit from caching, single-shot Q&A, reasoning needing all material at onceContext accumulates turn over turn. Cost and latency scale with length, and attention degrades well before the hard limit
ProgressiveMulti-turn dialogue, agent loops depending on recent state, staged workflows. The right default for most production workLong-range coherence, decisions depending on detail dropped earlier. Caching is harder and the exact input at step N is not reconstructable
RetrievalCorpora too large for context, sources changing faster than redeployment, citation requirementsSynthesis across many independently scored documents, chunking that splits tables or code, recall failures where the right document never enters top-k
CompactionLong-running agents where the full transcript is wasteful but recent state matters, phase transitions that can checkpointSummaries dropping load-bearing detail. The summariser is itself a model call, compaction is largely one-way, and measuring fidelity is unsolved

Production systems combine them. A long-running coding agent uses a monolithic cached prefix at session start, progressive recent state during work, just-in-time retrieval on discovery, and compaction once early exploration crowds the window. No single strategy carries that workload.

Four questions that design a context system

What does the model need at the start? That is the monolithic baseline. What does it need from recent steps? The progressive window. What might it need on demand? The retrieval layer. What earlier material can be compressed without losing decision-relevant detail? The compaction policy. Context strategy and context sizing are separate decisions, and treating them as one is where most designs go wrong.

Extended thinking, and gating model changes

Extended thinking adds a billed reasoning pass before the answer. Thinking tokens bill at the output rate and add latency. On Claude 4.6 and later, adaptive thinking with the effort parameter is the recommended control rather than a token budget. The older budget_tokens is deprecated on 4.6 and removed on Sonnet 5, where it returns a 400.

The decision rule: run evals without it first. Enable it only from a measured accuracy gap, never from the assumption that it cannot hurt.

Any model change is a behaviour change, so treat a swap as a release. You need three things: a curated test set covering the real distribution, a grading function, and a delta threshold set in advance. Set it after and you are not setting a standard, you are writing acceptance criteria after the build.

A document pipeline on Sonnet is over budget. The team builds a 250-document eval set stratified by document type and scores a Haiku migration. Sonnet averages 0.94, Haiku 0.86, with two document types at 0.71 and 0.74. The rollback criterion, agreed beforehand, was that no single document type may fall below 0.85.

What is the right call?

  1. Reject the migration, then route only the two weak types to Sonnet.
  2. Accept it, since the overall average of 0.86 remains close to target.
  3. Accept it provisionally and improve the two weak types by better prompting.
  4. Rerun the evaluation on a much larger sample before deciding either way.
Two lessons. First, the criterion was set before the data, so the team did not have to negotiate with itself. Second, stratifying by document type surfaced the salvage move. A single overall score of 0.86 would have hidden both the failure and the fix.

9Prompting as architecture

At enterprise scale a prompt is an asset you design, not a sentence you type.

A system prompt built for reuse has structure: role and scope, the constraints the model must hold, and an output contract naming the response shape. Reused at scale, ambiguity is a defect multiplied across every request.

A template is a system prompt with parameterised slots and fixed scaffolding, designed so the scaffolding carries the safety guarantees and filling a slot cannot remove a constraint. The safe path becomes the default path.

Description, one of the four AI Fluency competencies, is the discipline of naming the scope, the format and the constraints. The failure to watch for is underspecification: where the prompt is silent the model improvises, and improvises differently each time. Read a prompt for what it fails to say.

Caching mechanics

Cache breakpointsCaching works on a stable prefix. Mark the boundary between fixed and variable, and keep the fixed part genuinely fixed
Content orderingStatic before dynamic, always. The large unchanging block first, per-request content after the breakpoint
TTL selectionMatch cache lifetime to how often fixed content changes and how often the prompt is called
When not toWriting to cache has its own cost. Infrequent calls or a small fixed portion can cost more than they save

The module's failure case is a cache that never hit, because per-request content sat above the fixed instruction block. The prefix changed every request. The fix was reordering.

Library or Skill

RepeatabilityAssembled and often tweaked per useA stable procedure run the same way every time
DistributionOne codebase or teamAcross teams or products needing the same procedure
GovernanceLightweight, engineers own the fragmentsNeeds versioning, approval and rollback, which Skills carry

10Entry points, interfaces, routes, constraints

Three decisions in sequence: which entry point fits the work, which build-time interface suits the team, which delivery route fits the partner's cloud commitments.

Keeping them straight

API and SDK are the same entry point, different ergonomics. MCP and API tool use are different layers, not alternatives: MCP is how a tool is exposed and discovered across clients, API tool use is how Claude calls it in a request. The Agent SDK runs the loop; the Anthropic SDK does not. One request, one response: API or SDK. Reusable across clients: MCP. Multi-turn inside the partner's product: Agent SDK.

Claude Code layers: shaping and governing

Two distinct groups, and getting the split right is what makes an agent both useful and safe. Shaping what the agent knows and does: CLAUDE.md, Skills, subagents, MCP servers. Governing what it may touch: hooks, permission boundaries and approval flows, sandboxing and restricted execution. Permissions govern what the agent is allowed to touch; hooks govern what must happen before or after an action.

Delivery routes

The model behaves the same on every route. What differs is which cloud account the spend lands in, which identity system authenticates, which region traffic terminates in, and which procurement contract is already signed. The rule is not technical capability, it is what the partner has already committed to.

Anthropic first-party when there is no binding cloud commitment or the partner wants new features the day they ship. Bedrock, Vertex or Foundry when the partner already lives in that cloud. One tradeoff: CSP routes tend to lag the first-party API on new features by weeks.

When constraints decide for you

Some decisions are not yours. Attorney-client privilege, HIPAA, GDPR and residency, FedRAMP, or an internal policy rule entry points in or out before cost or ergonomics enter the conversation. Claude.ai consumer tiers are what this hits most often. API or SDK behind the partner's own gateway, with logging, retention and identity controls they own, is what usually survives regulated review.

Two details worth carrying: a HIPAA BAA covering one configuration does not extend to another, and beta features are generally excluded unless explicitly listed. Government routes run on a model lag, so the newest models reach GovCloud and Assured Workloads after commercial release.

How to phrase it

Name the governing constraint when you recommend an entry point, and let the constraint eliminate options before preferences do. That sentence is the Domain 6 skill hiding inside a Domain 1 decision.

A European insurer wants Claude embedded in an internal claims tool. Their engineering team works in Python, they hold a large committed AWS agreement, and their data protection officer requires that model execution be pinned to a named EU region with DPA terms inherited from an existing contract.

Which combination fits, and what decides it?

  1. Claude.ai with Enterprise controls, because strong governance features are clearly needed.
  2. Python SDK on the first-party API, because the team writes Python.
  3. Python SDK on AWS Bedrock, because residency and procurement together decide.
  4. MCP server on Bedrock, because tools should be reusable across clients.
Work the three decisions in order and notice which is forced. The entry point is a custom internal tool. The interface follows the team's language. The route is decided by residency and procurement, not preference. The DPO's requirement eliminates options before anything else is considered.

11The five takeaways

  1. Decomposition comes before architecture. Split the work across Claude, systems and humans first, driven by how the model behaves on each piece.
  2. Choosing a pattern is choosing how much autonomy to grant. Five factors decide it, and the tightest constraint wins.
  3. Reach for a tested reference architecture before inventing one. Combine only when parts break differently. Never substitute retrieval for live state.
  4. Start with Sonnet and treat every swap as a release. Eval set, grading function, rollback criterion set in advance. Progressive context outlasts monolithic.
  5. Pick the entry point by the work, not the shelf. The right recommendation is the one whose tradeoff you can name out loud as you make it.

Notice how much of that is restraint. Decompose before designing, use the known shape, start at the middle tier, choose by the work. The module's editorial position matches the engineering blog's: complexity has to earn its place.
