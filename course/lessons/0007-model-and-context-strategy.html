Model and context strategy

Two budgets and one decision. Which tier your evals clear, and what actually earns a place in the context window.

~20 minutes Domain 2, 13% of the exam 5 drills

This is the first Domain 2 lesson, and it is the one where the exam stops asking about shapes and starts asking about numbers. Tier, thinking mode, effort, cache breakpoints, batch discounts, window management. The individual facts are easy. The scoring happens on whether you reach for the right lever when a scenario gives you a latency SLA and a cost target at the same time.

The win by the end of this page: given a workload profile, you name the tier and the two knobs, and you can say which context in a long-running agent should never have been loaded in the first place.

Anthropic's own advice on choosing a model is worth quoting because it contradicts the reflex: "Tuning effort is often a better lever than switching models." Start at the default and move the knob before you move the tier. The other line to remember is the multi-model pattern, where a cheap tier handles the bulk of tokens and a frontier tier handles the hard minority. That is routing, from Lesson 0001, applied to cost rather than to task type.

Thinking and effort

These are two separate parameters and the exam will try to conflate them.

  • Adaptive thinking is thinking: {type: "adaptive"}, supported from Claude 4.6 onward. The model decides per request whether to think, and how much.
  • Extended thinking is the older type: "enabled" with budget_tokens. It is deprecated on 4.6, where requests still succeed, and 4.7 and later reject it with a 400. On 4.5 and earlier it is the only mode there is, and type: "adaptive" is what 400s there (extended thinking).
  • Effort is output_config.effort, with five levels: low, medium, high, xhigh, max. The default is high, and setting it explicitly is identical to omitting the parameter (effort).

Effort is a behavioural signal, not a token cap. It shapes every token in the response, including tool calls and preamble, so at low effort Claude batches operations into fewer calls and skips the commentary. The migration is mechanical: remove budget_tokens, set thinking to adaptive, and control depth with effort.

Prompt caching mechanics

BreakpointsUp to 4 per request
Prefix ordertools, then system, then messages. Each level builds on the previous, so a change high up invalidates everything below it
Write cost1.25x base input for the 5 minute TTL, 2x for the 1 hour TTL
Read cost0.1x base input
Minimum prefix512, 1,024, 2,048 or 4,096 tokens depending on the model. Opus 5 and Sonnet 5 are 512 and 1,024; Haiku 4.5 is 4,096
Below the minimumProcessed without caching. No error is returned. Check cache_creation_input_tokens and cache_read_input_tokens in the usage block; both zero means it silently did nothing

The break-even is straightforward arithmetic. A 5 minute write costs 1.25x and a read costs 0.1x, so one reuse inside the window already pays for the write. The 1 hour TTL at 2x needs a little more traffic to justify, and it is the right call when the gaps between calls are longer than five minutes but the prefix is stable all day.

The Batch API

Batch processing charges 50% of standard prices. Most batches finish inside an hour, results become available when everything completes or after 24 hours, and anything unfinished at 24 hours expires. A batch holds up to 100,000 requests or 256 MB. Results stay downloadable for 29 days. Caching stacks with the discount, though hits are best effort and land between 30% and 98%. It is the right answer for asynchronous volume and the wrong answer for anything a person is waiting on.

Context as a budget

Effective context engineering for AI agents makes the argument you need: models have a finite attention budget and every token spends some of it. Context rot is the measured consequence, where recall of anything in the window degrades as the window fills. A million token window does not repeal this, it just raises the ceiling on how much you can spend before it shows.

Four moves, and the exam wants you to pick between them rather than list them:

  • Compaction. Summarise a conversation nearing the limit and reinitiate a fresh window from the summary. For long sessions that must continue.
  • Structured note-taking. Persist notes outside the window and pull them back when relevant. For state that must survive compaction.
  • Just-in-time retrieval. Keep lightweight identifiers such as file paths or stored queries in context and load the bodies at runtime through tools. The counter-move to pre-loading everything.
  • Progressive disclosure. Expose capability metadata cheaply and load the body only on use, so the agent discovers context incrementally through exploration.
The whole lesson in one sentence

Pick the cheapest tier your evals clear and tune effort before you tune the tier, then treat the context window as a budget you spend rather than a container you fill.

Why this bites experienced people. If you have shipped RAG systems, stuffing feels like diligence: more context, more grounding, better answer. The million token window makes that instinct cheap to act on and expensive to hold. The second trap is caching. The prefix is invalidated by anything above the breakpoint that changes, so the harmless-looking timestamp or user ID at the top of a system prompt quietly costs you every cache read you thought you were getting, and nothing in the response tells you off.

SkillFive scenarios, name the lever

A retailer's product question widget answers shopper queries on the product page. Median response has to land under 1.5 seconds at peak, the questions are short and factual, and the current build runs Claude Opus 5 at default effort. Cost per session is running at three times the target.

What is the first change to make?

  1. Move to a faster tier and lower effort, then re-run the eval.
  2. Keep Opus 5 but raise effort to xhigh, cutting the retry rate.
  3. Send the traffic through the Batch API for the fifty percent discount.
  4. Add a second Opus 5 call that critiques and rewrites each answer.
Two constraints pointing the same way is a gift. Latency and cost both argue downward here, so the tier move is unambiguous. The order matters though: change the tier, then re-run the eval set, then decide whether effort needs to come back up. Anthropic's own line is that effort is usually the better lever, but that holds when only cost is failing.

A freight operator reconciles 380,000 customs declarations against invoices each night. The job starts at 10pm and results are needed by 6am. Nothing is interactive. The shared instruction block is roughly 300 tokens and every declaration body is different. Finance wants the cost down before the next quarter.

Which change gives the largest saving with the least design risk?

  1. Submit the work through the Batch API, which charges fifty percent less.
  2. Cache the shared instruction prefix and pay ten percent on later reads.
  3. Drop effort to low across the run and accept the capability reduction.
  4. Split each declaration across three parallel workers and merge their outputs after.
The 300 token detail was the trap. Below the model minimum, caching does nothing and reports nothing, so the option that normally saves the most saves zero here. Batch takes 50% off everything with no prompt changes at all. The volume needs four batches given the 100,000 request cap, which is a scheduling detail rather than a design risk.

A hospital's triage summariser has run for a year on Claude Opus 4.5 with thinking type enabled and a 10,000 token budget. The team is upgrading to a 4.7 model this sprint. The staging deploy returns a 400 on every single request and the on-call engineer has reverted twice.

What is the minimal correct fix?

  1. Set thinking type to adaptive, drop budget_tokens, and set depth with output_config effort.
  2. Keep thinking type enabled and lower budget_tokens until the request fits the window.
  3. Set thinking type to disabled and raise output_config effort to max for parity.
  4. Pin the deployment to Claude Opus 4.5 permanently and revisit the upgrade later.
Learn the version boundary as a pair, because the exam tests both directions. 4.6 deprecates extended thinking but still accepts it. 4.7 and later reject it with a 400. 4.5 and earlier reject adaptive with a 400. The one model where you legitimately set both is Opus 4.5, where effort shapes the response and budget_tokens sets thinking depth.

A newsroom tool prepends a 30,000 token style guide and archive index to every request, then appends the reporter's current draft. Volume is steady through the working day with calls every few seconds. The team set one cache breakpoint after the draft and the usage block shows no cache reads at all.

Why is the cache not hitting?

  1. The breakpoint sits after text that changes each request, invalidating the prefix.
  2. The style guide sits below the model minimum, so caching is skipped.
  3. Only one breakpoint was set, and four are required for any hit.
  4. The five minute window expired between requests, so every write went cold.
A cache breakpoint marks the end of a prefix, not the beginning. Everything above it has to be byte-stable, so putting the marker after the draft means the cached prefix includes the draft and therefore never repeats. The fix is one line: move the breakpoint to the end of the static block. Then confirm it worked by reading the usage fields, because failure is silent either way.

A tax authority's caseworker agent runs for hours per session, calling six tools and accumulating full document bodies in the transcript. Accuracy on facts stated early in a session has been falling as sessions get longer. The team's fix so far has been moving to a one million token window, which bought a little time and then stopped helping.

Which two moves actually address the failure?

  1. Compact the transcript into a summary and restart with that summary.
  2. Return file references from tools and load bodies only when needed.
  3. Raise output_config effort to max so the model reasons more carefully.
  4. Move to a larger context window and load every document upfront.
  5. Add a one hour cache breakpoint so the transcript costs less.
The failure signature is context rot, and the giveaway is that a bigger window helped briefly then stopped. That pattern means the problem scales with occupancy rather than with the ceiling. Compaction shrinks what is already there, and just-in-time retrieval stops it arriving. Option E is the one to sit with: it is a real optimisation, aimed at the wrong quantity.
