Claude Platform & Solution Design · Lesson 0002

Splitting the work: Claude, system, human

A business request arrives as one blob. Your first move is not picking a pattern, it is cutting the blob into three piles and defending the cuts.

~18 minutes Domain 1, 17% of the exam 5 drills

Lesson 0001 was about which tier to build. This one runs earlier in the conversation. Before there is an architecture there is a sentence from a stakeholder, usually something like "we want AI to handle claims", and the whole job is deciding which parts of "handle" belong to a model, which belong to ordinary code, and which stay with a person who can be named in an audit.

The win by the end of this page: given an ambiguous request, you draw three boundaries out loud, you can say what breaks if each one moves, and you can hand the result to an implementation team you will never sit with.

KnowledgeThree owners, one rule for choosing

The rule is a cost ladder. Give each job to the cheapest owner that can do it correctly and prove it later. Code is cheapest and most provable. Claude is next. A human is the most expensive owner you have, and also the only one who can be accountable, which is why you spend that budget deliberately rather than by default.

Who should own a job
OwnerGive itBecauseThe tell in a scenario
Deterministic code Exact lookups, arithmetic, format validation, thresholds, retries, logging Reproducible, testable, near free per call, still true in three years A published list, a schema, a formula, a regulator, high volume
Claude Messy language, fuzzy classification, synthesis, drafting, judgement over unstructured input No rule set covers the tail, and sensible people would write different rules "Free text", "varies", "unstructured", "edge cases", "however the customer phrases it"
Human Irreversible actions, contested judgement, the signature on a decision Someone has to be answerable, and able to stop the thing An appeal, a regulator, money movement, an external send, a permanent delete
The whole lesson in one sentence

Give each job to the cheapest owner that can do it correctly and prove it later, and code is cheaper than Claude, which is cheaper than a human.

What code should have kept

Anthropic's own guidance keeps pushing work down the ladder. The Skill authoring best practices page argues for pre-written utility scripts over model-generated code because they are "more reliable than generated code", save tokens, and "ensure consistency across uses". Writing effective tools for agents makes the same move at the tool boundary: consolidate operations so you "offload agentic computation from the agent's context back into the tool calls themselves". And when it comes to grading, Define success criteria ranks code-based grading as the fastest, most reliable and most scalable option, with human grading marked avoid if possible.

So the first failure mode is asking a model to do work a database query, a regex or a subtraction would do exactly. It is slower, it costs per call, it drifts between model versions, and it cannot be re-run on audit to produce the same answer. If the scenario tells you a list is published, a format is standardised or a threshold is written in policy, that job has already been assigned and it is not to Claude.

The opposite failure, which is more expensive

The second failure mode is over-constraining: pinning the model inside a rule engine until it is only filling slots. You know you have done it when a growing share of real inputs falls outside the rules and lands in a manual queue. The rules were never going to cover the tail, which is exactly the part you bought a model for. Deleting rules is the fix, not adding more.

Why this bites experienced people. Ten years of shipping teaches you that a service you do not have to maintain is a service that cannot break, so "Claude can just do that" feels like a simplification. On this exam it reads as a control weakness. A regex a graduate can read beats a prompt that works 99% of the time, because the regex is identical next year and costs nothing at a million calls a day.

Where the human actually goes

Anthropic's framework for safe and trustworthy agents puts it as keeping humans in control while enabling autonomy: humans "should retain control over how their goals are pursued, particularly before high-stakes decisions are made". Two tests decide it.

  1. Reversibility and blast radius. Can this be undone, and how much damage lands before anyone notices? Refunds, production writes, outbound messages and deletions fail this test. Internal notes and draft artefacts pass it.
  2. Accountability. Is there a decision someone must own by name, because it can be appealed, audited or defended in court? A regulated denial has a clinician's name on it. No confidence score substitutes for that.

Anything failing neither test does not earn a gate. Gate everything and you destroy the efficiency case that funded the project, which is a design error, not caution.

Writing the boundary down

The deliverable is not a diagram. A diagram shows wiring without saying who decides. Give the build team a row per step with these columns, and the system becomes buildable by people you will never meet.

The handoff table
ColumnWhy the build team needs it
StepOne named unit of work, small enough to test on its own
OwnerCode, Claude or human. Exactly one of the three, never "both"
InputWhat arrives, and from where. Names the upstream contract
Output contractShape and validation. This is what lets code check the model's work
Failure behaviourRetry, fall back, or stop and escalate. Silence here becomes an outage
GateBlank, or the named human role that must approve before it proceeds

In Claude Code terms these columns already have homes, which is worth knowing because the exam likes concrete mechanisms. The Agent SDK loop puts the code gate in a PreToolUse hook that can block a call before it runs, the human gate in permission modes and the approval callback, and the deterministic stop in max_turns and max_budget_usd. Hooks run in your process, not the model's context, which is the point: the guarantee is not something the model can talk its way past.

SkillFive requests, three piles each

Read the last sentence first, find the constraint that eliminates options, then answer. The reason matters more than the score.

A retail bank screens 2 million payments a day for sanctions exposure. The list is published by the regulator, changes weekly, and every hit must be reproducible on audit years later. Analysts separately want a plain-English note explaining why an unusual payment pattern looks odd.

How should the work split?

  1. Code matches the list, Claude writes the pattern note, analysts decide.
  2. Claude matches the list and drafts the note, analysts review everything.
  3. Code matches the list and writes the note, skipping analyst review.
  4. Claude matches the list, code writes the note, analysts approve everything.
The binding constraint was reproducible on audit years later. That phrase assigns the matching step before you finish reading. Published list plus exact match plus enormous volume is the clearest code job in the whole domain, and the only work left for a model is the part with no correct answer written down.

A health payer wants faster prior authorisation. Approvals follow published clinical policy. Denials are regulated: a named clinician must own each one, and the member can appeal it. Volume is 12,000 requests a week and the medical directors are already at capacity.

Which split survives an appeal?

  1. Claude issues approvals and denials, clinicians sample ten percent afterwards each week.
  2. Claude drafts the case, code applies policy thresholds, a clinician signs denials.
  3. Clinicians review every request, with Claude summarising the notes for them first.
  4. Code issues approvals and denials, with Claude explaining each outcome to members.
Two constraints were doing work at once. The appeal right forces a named human onto the denial path, and the capacity line forbids a human on every path. That is the shape of most real governance answers: a gate on the branch that can be contested, automation everywhere else.

A freight forwarder is putting a Claude assistant over its shipment tracking stack. Five jobs are currently drafted as model calls. Margin per shipment is thin and the platform moves 90,000 shipments a month.

Which two jobs should move out of the model and into ordinary code?

  1. Deciding which of six exception templates fits a garbled driver message.
  2. Recomputing arrival times from the carrier distance table and traffic feed.
  3. Summarising a fortnight of delay notes into a paragraph for customers.
  4. Judging whether a damage photo description warrants a goodwill credit offer.
  5. Extracting the container number, whose format is fixed by ISO standards.
Both answers share a property: there is exactly one correct output and a rule already defines it. Volume and thin margin sharpen the point but do not create it. The three you left with Claude all have the opposite property, which is that two reasonable people would produce different output and neither would be wrong.

A council triages housing repair reports from residents. The team built a 180-rule decision tree and now uses Claude only to fill fixed slots inside it. Six months on, 40% of reports fall outside the tree and drop into a manual queue that takes eleven days to clear.

What is the correct change?

  1. Extend the decision tree with rules covering the forty percent that escaped.
  2. Replace the whole triage stack with an autonomous agent holding repair tools.
  3. Let Claude classify the free text, keeping code for eligibility and dispatch.
  4. Retain the existing decision tree, adding a second model voting on outputs.
This is the over-constraining failure, and the tell is always the same: a manual queue that grows. The model was hired for the tail and then forbidden from touching it. Note what does not move, though. Eligibility and dispatch stay in code, because they are published policy and the council has to show its working.

You have agreed the split for a retailer's returns assistant. An offshore team of nine builds it next sprint and you will not be in their standups. Two steps in the flow are irreversible: issuing the refund and writing off stock.

What do you hand them?

  1. A system prompt describing every rule, so the model applies them consistently.
  2. A table naming each step's owner, contract, failure behaviour and approval gate.
  3. An architecture diagram showing the services, queues and model calls in order.
  4. A prompt library with tested examples covering the common returns cases seen.
The consulting half of this exam is graded too, and this is what it looks like. A boundary you cannot hand over is a boundary you have not drawn. The two irreversible steps are why the gate column exists: a team that never meets you should be unable to build the refund path without noticing it needs an approver.
