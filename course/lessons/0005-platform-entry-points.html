Claude Platform & Solution Design · Lesson 0005

Platform entry points

Same architecture, five different front doors. The exam tests whether you can match a scenario's user, governance posture and team maturity to the surface the solution ships through.

~18 minutes Domains 1 and 2, 30% of the exam 5 drills

Lessons 0001 and 0004 settled what to build. This one settles where it lives. The distinction matters commercially: the same routing workflow costs nothing to deliver as an Enterprise connector and costs a quarter of engineering time to deliver as a bespoke Agent SDK service, and the difference between those two is usually who the user is rather than what the model does.

The win by the end of this page: given a scenario, you name the entry point, name the governance story it comes with, and spot the sentence that quietly ruled out one of the others.

The whole lesson in one sentence

Pick the entry point from who the user is and what evidence the auditor needs, not from how sophisticated the architecture is.

The three that get confused

Messages API versus Agent SDK. The Messages API is one endpoint, POST /v1/messages, with client SDKs in Python, TypeScript, C#, Go, Java, PHP and Ruby. You write the tool loop. The Agent SDK is the Claude Code agent loop as a library, "programmable in Python and TypeScript", and it hands you built-in tools, hooks, subagents, MCP, permissions, sessions, skills and memory loading. The docs draw the line as: use the Client SDK if you are "calling the API directly and implementing the tool loop yourself", use the Agent SDK for "building an agent without implementing the tool loop yourself". Two things constrain the choice. The Agent SDK is a library for Python and TypeScript only; from any other language you run the CLI as a subprocess with -p and --output-format json. And Anthropic does not permit third-party products to offer claude.ai login or subscription rate limits, so a product you ship on the Agent SDK authenticates with API keys.

Claude Code as a product surface. Headless mode makes Claude Code a component rather than a terminal: claude -p "..." with --output-format json or stream-json, --json-schema for structured output, --allowedTools to pre-approve, and a permission mode baseline. In CI, --bare skips auto-discovery of hooks, plugins, MCP servers and CLAUDE.md so the run is identical on every machine, and --permission-mode dontAsk denies anything not explicitly allowed. The same engine runs in GitHub Actions, which checks that the triggering user has write access and rejects bot actors, and can authenticate through OIDC workload identity federation so no long-lived key sits in the repository.

MCP is an integration surface, not an application. The architecture overview is explicit that a host such as Claude Code or Claude Desktop creates one client per server, and that "MCP focuses solely on the protocol for context exchange, it does not dictate how AI applications use LLMs or manage the provided context". A server exposes three primitives: tools, resources and prompts. Stdio transport serves one local client; Streamable HTTP serves many remote clients and supports bearer tokens, API keys and OAuth. So the question "should we build an MCP server" is never an alternative to "should we build an application". It is the answer to "how many clients need this same data".

The governance column is usually the deciding one

Enterprise is where the audit story lives. The Compliance API gives programmatic access to organisation activity for compliance and SIEM feeds, and it covers claude.ai organisations including chats, files and projects, Cowork sessions, Claude Code sessions, and the user directory. Console customers get the Activity Feed only. For Claude Code specifically, OpenTelemetry export gives metrics such as token and cost usage, tool permission decisions and commit counts, plus event logs, with prompt and response content redacted by default until an admin explicitly turns it on. Managed settings can lock that configuration so a developer cannot override it locally.

Why this bites experienced people. If you build on Claude Code every day, it is the surface you reach for, and it is genuinely the cheapest way to ship agentic behaviour to developers. But roughly half of exam scenarios put a non-developer in front of the system: an underwriter, a caseworker, a clinician. The moment the user does not live in a repository, Claude Code is the wrong door no matter how well it would do the work. Read the first sentence of every scenario for the user's job title before you read anything else.

SkillFive scenarios, thirty seconds each

The binding constraint in this lesson is usually the user, the regulator, or the size of the team you have.

A broadcaster keeps its rights-clearance data in one internal service. Three groups need it: the newsroom team who work in Claude Desktop, the platform engineers who work in Claude Code, and a scheduling application the company is building itself. The data model changes about once a month and all three must stay in step.

What should the integration team build?

  1. One remote MCP server, with all three clients pointed at it.
  2. One Agent SDK service wrapping the database, called by each client.
  3. Three bespoke integrations, one for each client, sharing a REST layer.
  4. A nightly catalogue export loaded into a shared project knowledge base.
The tell is the client count, not the sophistication of the task. MCP is an integration surface: one server, many hosts, each host creating its own client. Streamable HTTP is the transport that serves many remote clients and carries OAuth. If a scenario names two or more places the same data has to appear, the answer is a server rather than a second application.

A health insurer wants an agent that reads a claimant's full document bundle overnight and produces a coverage summary. A run takes about forty minutes across many tool calls and needs persistent session state. The insurer's contract requires a signed HIPAA business associate agreement covering everything the workload touches, and it has a competent platform team.

Which entry point should the design assume?

  1. The Agent SDK, running the agent loop inside your own infrastructure.
  2. Managed Agents, so Anthropic runs the harness, sandbox and session state.
  3. Claude Code headless, invoked overnight from your existing scheduler and runners.
  4. The Messages API alone, with your service implementing the whole loop.
This is the archetype of a quiet disqualification. Every clue in the scenario points at Managed Agents, long-running, stateful, no harness to build, right up until the compliance clause. Managed Agents is in beta with limited Zero Data Retention and HIPAA BAA coverage because of its stateful design. One sentence about a regulator can override four sentences about fit.

A bank is rolling AI-assisted development out to 400 engineers. The regulator has asked for evidence of which changes were AI-assisted, what the model was permitted to run, and proof that individual engineers cannot loosen the policy on their own machines. The bank already has an SIEM and a central OpenTelemetry collector.

What is the defensible configuration?

  1. Enterprise Claude Code with managed policy settings and Compliance API export.
  2. Console API keys per developer, with the usage dashboard for review.
  3. Agent SDK wrappers per team, each logging into separate private stores.
  4. Claude Desktop seats with connectors, and quarterly attestation from each lead.
Three requirements, three features, and they map one to one: which changes were AI-assisted goes to OpenTelemetry, what the model could run goes to managed policy settings, and cannot be overridden locally is the whole point of managed settings. Remember the default: prompt and response content is redacted in telemetry until an admin explicitly enables it, which is usually the answer to the privacy objection that follows.

A retailer regenerates category copy for 40 million product records every weekend. Nothing is interactive, nothing is agentic, and the whole job simply has to be finished before Monday trading. The finance director has already flagged the projected inference spend as the reason the project might not go ahead.

Which entry point should the proposal name?

  1. The Message Batches API, accepting the asynchronous turnaround for half price.
  2. The Messages API synchronously, fanning out across your own worker pool.
  3. Claude Code headless in CI, one print-mode invocation per product record.
  4. Managed Agents on a cron schedule, one session per catalogue partition.
The examinable point is that entry point selection is a cost lever, not only an architecture one. Batch processing is a 50% discount for work that can wait, and a weekend window is the clearest possible signal that it can. When the scenario names a finance objection and a generous deadline in the same paragraph, it is pointing at batch.

A benefits agency wants 900 caseworkers to be able to ask questions about policy guidance and their own case notes. The caseworkers are not technical, the agency has no spare engineering capacity, the deadline is six weeks, and everything the caseworkers do is subject to freedom of information requests and a records retention schedule.

Which two moves fit the constraints?

  1. Enterprise seats for the caseworkers, plus a connector to case records.
  2. A bespoke Agent SDK application, built and hosted by the department.
  3. Compliance API pulls into the agency records retention and disclosure pipeline.
  4. Claude Code licences for caseworkers, with permission modes locked to dontAsk.
  5. A direct Messages API integration written into the case management screens.
Both right answers avoid writing software. Team maturity and capacity are architecture inputs, not excuses, and the exam grades the consulting half. Note also that the two answers are different kinds of thing: one is the surface the users touch, the other is the evidence the auditor gets. A complete entry-point answer usually names both.
