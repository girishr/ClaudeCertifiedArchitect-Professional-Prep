Augmented call, workflow or agent, plus the multi-agent case.

The work is split. Now: what shape does Claude's involvement take? Three patterns, and each takes a different position on two axes, how predictable the path through the work is, and how much autonomy you are willing to hand the model.

Three patterns
PatternWhere control flow livesUse it when
Augmented LLM
High predictability, low autonomy		 In your code. One bounded call, possibly with tools, retrieval or extended thinking. The flow never branches on what the model decided The task is well defined, the output is verifiable, and there is no reason to split the work
Workflow
Predictable shape, bounded judgment per step		 In your code. Named steps you orchestrate; each step may or may not call Claude Error cost is real, observability matters, and the steps can be written in advance
Agent
High autonomy, low predictability		 Inside the model. You give a goal and tools; the model picks its own sequence Only when the path genuinely cannot be enumerated in advance, and only when an unexpected output is acceptable and recoverable

In production, agents are bound by constrained tool entry points, per-turn budgets, explicit permissions and stopping criteria. The module is blunt that these are not optional extras: they are what keeps an agent from becoming a liability.

5.1Four workflow sub-patterns

Choosing a workflow does not finish the design. Four shapes, each a different assumption about how the steps relate.

The four sub-patterns
Sub-patternShapeWhen it earns its place
ChainingStep 2 consumes step 1's output, sequentiallyNatural stages with clean handoffs: extract, then classify, then summarise
RoutingA classifier, often Claude, picks the downstream pathInputs vary in kind and different kinds need different handling
ParallelisationConcurrent calls, results aggregated or votedSub-tasks are genuinely independent: twelve contracts, twelve reviews, one report
Evaluator-optimizerOne call drafts, a second grades and returns feedback, loop until a criterion or a retry capQuality is verifiable but a single attempt is not reliable enough

They combine. Most production workflows use more than one. Pick the simplest shape that meets the error tolerance and observability requirement, then revisit once you have production data. Escalate when measurement shows the simpler pattern falling short, not before.

A qualifier the module is careful about. Agents are not automatically more expensive than workflows. What drives cost is how much context accumulates and how many calls are made. A badly designed workflow can cost more than a well-designed agent. Design matters more than the label.

5.3Prompt before you fine-tune

When prompting feels unreliable the instinct is fine-tuning. On Claude that is usually the wrong first move. The sequence: optimise the prompt, then add tools or retrieval, then move to a stronger pattern such as evaluator-optimizer, and only then consider fine-tuning. Fine-tuning earns its place at very high volume where inference cost is the constraint, where latency demands a smaller specialised model, or where a consistent output format has resisted every prompting attempt. Otherwise it pins you to a fixed model version for little gain. Availability is limited and varies by model and route, so confirm before recommending it to a partner.

5.4Multi-agent: orchestrator and subagents

Some problems exceed what one agent can hold in one context. Then the design becomes an orchestrator that decomposes and synthesises, and subagents that each carry a scoped piece in their own context. The orchestrator never does the sub-task work itself.

Three things must be designed rather than assumed: how the work is split, how each subagent's result is structured so it can be combined, and how the orchestrator resolves conflicts and gaps.

Failure modes and the design response
FailureWhere it landsResponse
A subagent returns malformed or empty outputSubagent boundary, recoverableValidate every result; retry or re-route; record the gap rather than failing the run
Two subagents conflictSynthesis, recoverableGive the orchestrator an explicit conflict rule, or escalate to a human
The orchestrator loses the goal or its stateOrchestrator, often unrecoverableProtect orchestrator state; checkpoint so a failed run resumes rather than restarts
Traces fragment across componentsObservability, cross-cuttingPropagate one shared trace identifier so a run is reconstructable end to end

5.5Watch out, twice

Flexibility bought non-determinism. A team picked an agent because they did not want to constrain the design too early. By month two they had added so many guardrail tools that they had rebuilt the workflow inside the agent loop, minus the logging. When compliance asked which step approved a disbursement, they could point only at a model turn, and the model version had rolled forward two weeks earlier with no re-validation. When they mined the traces, the real paths through the system fell into four shapes, all knowable from week one. A router and four chains would have been the answer.

Note the module separates two failures there. The audit gap is about the agent pattern. The unpinned model version is a governance gap that a workflow would have inherited just as easily. Only one of them is an argument against agents.

Fan-out hid a dropped unit. A compliance team fanned a 50-section contract out to one subagent per section and synthesised: 48 sections reviewed, 3 flagged. Two sections had never been reviewed, one subagent timed out and one failed to parse a scanned page. Nothing reconciled results returned against units dispatched, so 48 returned results became 48 reviewed instead of two are missing. The summary read as complete, which is exactly what made it dangerous.

A draft multi-agent design for a large document-classification job lists six components: (1) the orchestrator splits the corpus into per-document units, (2) subagents run in parallel and each returns a verdict, (3) synthesis sums the returned verdicts into a report, (4) an irreversible auto-archive action runs with no human gate, (5) no retry or gap flag on a failed subagent, (6) a shared trace ID is propagated to every subagent.

Which two carry a control or failure-boundary defect?

  1. Component 4, the ungated irreversible action
  2. Component 1, the decomposition into units
  3. Component 5, the missing retry and gap flag
  4. Component 6, the shared trace ID
Components 4 and 5. Component 3 is also weak, because summing returned verdicts without reconciling them against units dispatched is the dropped-unit failure. If the item had asked for three, that would be the third. Work the boundaries: every dispatch needs a count that must match, and every irreversible action needs a gate.
