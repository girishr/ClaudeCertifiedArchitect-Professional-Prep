Model and context strategy

Tier choice, the context budget, and the eval gate on every swap.

Before you read

The claims triage assistant is going to build. Claude reads each claim into a schema and drafts the adjuster's email; priority and coverage stay with the partner's systems. The team has to name a model tier before the first eval exists. Which tier do you start on?

Locked in. The section will not tell you whether you were right until the end.

You have a pattern and an architecture. You do not have a shippable system. Three decisions remain, and each one sets what the same architecture costs at production volume: which model, how much of the window to use, and whether context arrives progressively or all at once.

8.1Four terms people conflate

Keep these apart or the architecture blurs
TermWhat it actually is
Context windowThe model's active attention space. Everything inside is available for reasoning; everything outside does not exist to the model. It resets between calls unless your application manages continuity
RetrievalExternal knowledge fetched at query time from a corpus the model does not hold. It augments the window, it does not replace it. The model sees only what the retriever surfaced
Persistent application stateOwned by your system, not the model. Order status, user records, balances. Reaching it requires a tool call
Summaries and memory layersContinuity your application manages across turns or sessions. The model has no native memory between calls. Anything that persists does so because you stored it and passed it back

8.2Model selection: Sonnet by default, moves by evidence

Opus, Sonnet and Haiku trade cost, latency and capability differently. Sonnet is the default starting point. Move up to Opus only when an eval set says Sonnet is not meeting the quality bar. Move down to Haiku only when an eval set confirms the trade-off is acceptable for the specific task. Measured, not reflexive.

8.3The window is a ceiling, not a target

Everything entering the window is counted in tokens: system prompt, conversation history, retrieved documents, tool outputs, and the model's own responses. Two constraints follow, and both show up in design: the window has a fixed limit, and you are billed per token on every call.

How much text a token covers varies by model generation, tokeniser and language, so treat any characters-per-token ratio as illustration. Measure instead: the usage field on every response reports what actually counted.

8.4Four context strategies, usually layered

Where each earns its place and where it breaks
StrategyEarns its placeBreaks down
Monolithic
Load everything into one prompt		 Bounded tasks with predictable input size. Stable prefixes that benefit from caching. Single-shot Q&A. Reasoning that genuinely needs all material at once Conversations and tool loops where context accumulates. Cost and latency scale with length, and attention quality can degrade well before the hard limit
Progressive
Carry forward only what the next step needs		 Multi-turn dialogue, iterative refinement, agent loops, staged workflows with narrow handoffs. The right default for most production workloads Tasks needing long-range coherence. Decisions depending on detail dropped earlier. Caching is harder when the carried context mutates, and the exact input at step N is no longer reconstructable, which complicates debugging
Retrieval
Fetch relevant chunks at query time		 Knowledge bases too large for context. Sources that change faster than the prompt is redeployed. Queries needing only a slice. Cases where citation is required Synthesis across many documents scored independently. Chunking that splits tables, code or multi-paragraph arguments. Recall failures where the right document never enters the top-k
Compaction
Periodically summarise accumulated context		 Long-running agents and conversations where the full transcript is wasteful but recent state matters. Phase transitions that can checkpoint to a clean summary Summaries that drop load-bearing detail: identifiers, numbers, prior decisions, an edge case mentioned once. The summariser is itself a model call with cost and failure modes, and compaction is largely one-way
Four questions that design a context system

What does the model need at the start? That is the monolithic baseline. What does it need from the most recent steps? The progressive window. What might it need to fetch on demand? The retrieval layer. What earlier material can be compressed without losing decision-relevant detail? The compaction policy. Context strategy and context sizing are separate decisions that interact but do not determine each other, and treating them as one is where most context designs go wrong.

8.5Extended thinking is a bill, not a mode

Extended thinking is a per-request capability: the model works through the problem in a separate block of thinking tokens before answering. Control has changed across generations. On Claude Opus 4.6 and later, Sonnet 4.6 and later, and Sonnet 5, adaptive thinking with the effort parameter is the recommended control, so you set how much reasoning effort to apply rather than configuring a token budget. Adaptive thinking is the only mode on Claude Fable 5. The older manual budget_tokens is deprecated on the 4.6 generation and removed on Sonnet 5, where it returns a 400.

Thinking tokens bill as output tokens and add latency. When extended thinking is not engaged, none are generated and none are billed. The model reasons internally either way; what you are choosing is whether to pay for an expanded pass. Run evals without it first. Turn it on because a measured accuracy gap says so, not because it cannot hurt.

8.6Gate every model change with an eval

A model swap is a change to the system's behaviour, so treat it as a release. Three things, minimum:

  1. A curated test set of prompts with known-good outputs, covering the real distribution of work.
  2. A grading function, model-graded against a rubric or programmatic where the check can be expressed in code.
  3. A delta threshold set in advance. Set it after and you are not setting a standard, you are writing the acceptance criteria after the build.

8.7Watch out: Opus everywhere, seven times the budget

Ninety days after launch, monthly cost was running at seven times the model. Median latency on the user-facing path was 2.3 seconds against an agreed 800 millisecond target. Satisfaction scores had not moved. Every call in the stack was Opus, because there had been no per-step model decision, because there had been no per-step eval that would have forced one. Extended thinking had been left on for a routing classifier that does no reasoning.

Place your bet before the reveal

The fix was retroactive: build the eval set, then put each step on the tier the eval said it earned. Where did cost land, and what happened to satisfaction?

The fix, retroactively: build the eval set, route the classifier to Haiku, mid-pipeline summarisation to Sonnet, keep Opus only on final response composition where the eval said it earned its place. Cost fell 71 percent, latency to 940 milliseconds, satisfaction unchanged.

The line worth carrying into the exam

Not choosing a model tier is choosing the most expensive one. The absence of a deliberate choice is not neutral.

Same question, after the section

The claims triage assistant, before the first eval exists. Which model tier do you start on?

A trading desk wants a one-line natural-language summary of each executed trade, delivered within 400 milliseconds. Volume is high and constant. A proposal suggests Opus with extended thinking enabled, monolithic context carrying the full session history, on the grounds that accuracy matters in finance.

Which single change does the most to make this shippable?

  1. Enable prompt caching on the system prompt
  2. Turn extended thinking off and re-measure before anything else
  3. Switch to Haiku immediately to cut latency
  4. Split the summary into a two-step workflow
Extended thinking comes off first. It is the cost and latency lever with the clearest case against it here: a one-line summary of a bounded input is not reasoning work, and nobody has produced a measured accuracy gap to justify the pass. Monolithic session history is the second problem and progressive context is its fix. The tier question comes last, and it comes with an eval set attached.
