The brief

A 180-lawyer mid-market firm wants to speed up contract review. Senior associates spend an estimated 12 to 18 hours a week reading vendor and partnership contracts to flag clauses that conflict with the firm's standard playbook. Average contract length is 35 pages. Current output is a redlined PDF with margin comments. The firm uses iManage for document storage, has a private LLM gateway approved by their CIO, and is bound by attorney-client privilege requirements that exclude consumer-grade tools. Target: cut associate time per contract by 60 percent while keeping the senior associate as final reviewer.

Before reading further, write one paragraph covering all five decisions: entry point, pattern, the split across Claude and existing systems and humans, model and context strategy, and the human-in-the-loop posture.

11.1Reading the brief for constraints

Every sentence in the brief is doing work
In the briefWhat it decides
Attorney-client privilege, consumer tools excludedRules out Claude.ai as the entry point before anything else is discussed
A CIO-approved private LLM gatewayThe route already exists. The build-time interface is the API or SDK behind the firm's own app
iManage for storageDocument fetch belongs to an existing system, not to Claude
A standard playbookA versioned source of truth the firm maintains. Retrieve it, do not bake it into the model or freeze it in a prompt
35 pages, clause by clauseIndependent units. Parallelisation is the workflow sub-pattern
Senior associate stays the final reviewerThe human gate is fixed by the brief, not chosen by you

11.2The four candidate architectures

All four commit to all five decisions. Three fail on exactly one. That is the diagnostic skill: find the single decision that breaks each one.

What fails, and where
OptionVerdict
A. Claude.ai, associates upload each contract into a Project holding the playbook as reference files. Parallelised review by section. Sonnet, progressive context. Senior associate reviews everythingFails on the entry point. The pattern, model and human gate are all fine. Privilege excludes the consumer-grade surface, and that constraint was stated in the brief
B. API or SDK behind a thin internal app, SSO, approved gateway. The playbook loaded into the system prompt in full on every call. Parallelised by section. Sonnet. Senior associate reviews everythingFails on context strategy. A monolithic playbook on every call is the working-memory cliff and the silent budget killer, and it freezes a document the firm updates. Retrieve the playbook per clause
C. API or SDK behind a thin internal app, SSO, approved gateway. An open-ended agent given the contract and the iManage tools, deciding for itself how to work through the document. Playbook retrieved per clause. Opus on every call. Senior associate reviews everythingFails on pattern, and on tier. The path through a 35-page contract is enumerable, so autonomy buys nothing and costs audit clarity in a privileged setting. Opus everywhere is the untested default the module warns about
D. API or SDK behind a thin internal app, SSO, approved gateway. Parallelised review by section with an evaluator pass enforcing a strict schema on flagged clauses. Claude extracts, classifies against the playbook and drafts redlines. The playbook stays in the firm's systems as a versioned source of truth, retrieved per clause. iManage fetches documents. Sonnet with progressive context, extended thinking per clause only where an eval justifies it. Senior associate signs off on every output, low-confidence clauses flaggedHolds. Every constraint in the brief is respected and every decision is one you can defend out loud

Same firm, same brief. A fifth proposal arrives: API behind the approved gateway, parallelised clause review, playbook retrieved per clause, Sonnet with progressive context, iManage for fetch. The only change is that low-risk clause categories are auto-approved without associate review, to hit the 60 percent time saving more comfortably.

What does that change cost, and is it acceptable?

  1. Acceptable, because sampling low-stakes work is exactly what the module recommends
  2. Unacceptable, because it raises cost per contract above the target
  3. Acceptable, provided an eval set confirms the low-risk classifier is accurate
  4. Unacceptable, because the brief fixed the human gate and accountability sits with the reviewer
The gate was a requirement, not a preference. The strongest habit for this domain is to separate what the brief fixed from what it left to you. Fixed here: privilege, the gateway, iManage, the final reviewer. Left to you: pattern, sub-pattern, tier, context strategy, and where retrieval fits. An option that optimises a fixed constraint is wrong however sensible it sounds in isolation.
