The other major lever alongside model and context is the prompt itself. At enterprise scale a prompt is not a sentence you type, it is an asset you design, version, cache and govern. Four screens in the official module, and the part of it least visible from the published exam objectives, which is exactly why it is worth reading twice.

9.1The system prompt as a designed artifact

A system prompt for a one-off chat and one that hundreds of requests a day depend on are different things. The enterprise version has structure: a clear statement of role and scope, the constraints the model must hold, what it must never do and what it must always do, and an output contract naming the shape the response has to take. At scale, ambiguity is a defect multiplied across every request.

A template is a system prompt with parameterised slots and fixed scaffolding around them. The design goal is that the scaffolding carries the consistency and safety guarantees, so filling a slot cannot accidentally remove a constraint. A good template makes the safe path the default path: the person using it supplies the variable content and inherits the guardrails without re-authoring them.

Description, as a competency

Telling the model precisely what you want: the scope (what is in and out of bounds), the format (the exact output contract), and the constraints (rules that must never be violated). The failure to hunt for is underspecification. Where the prompt is silent, the model improvises, differently each time, which is exactly the non-determinism you did not want in a reused asset. Read a prompt for what it fails to say.

9.2Technique follows task complexity

Three techniques
TechniqueWhat it isWhen it fits
Zero-shotInstruction only, no examplesWell-specified tasks the model already handles. The default to try first
Few-shotA handful of input and output examples in the promptTasks where the format or the judgment is easier to show than to describe
Chain-of-thoughtPrompt the model to reason step by step before answeringMulti-step reasoning, interacting conditions, tasks where the path matters to the answer
The module's own worked calls. Pick the technique before the reason shows
TaskTechniqueWhy
Classify a support ticket into five named categories Make your call first.Well specified, categories named, classification is reliable without examples
Extract date, vendor and amount from receipts with wildly varying layouts Make your call first.The extraction format is easier to demonstrate than to describe, especially across layouts
Decide whether a clause creates liability under three interacting conditions Make your call first.The answer depends on a sequence of conditional steps; reasoning aloud reduces skipped interactions
Summarise 400 words into two sentences Make your call first.Bounded input, standard task. Examples or reasoning add tokens with no quality gain

Two more things the module is explicit about. First, the same prompt does not behave identically across tiers or generations. A more capable model may need less scaffolding; a less capable one may need more. A prompt tuned for one model is a starting point for another, which is the underlying reason a model swap is treated as a release: the prompt-model pairing is what you ship. Second, bias gets built in through construction: leading phrasing, few-shot sets that show only one kind of case, assumptions baked into the instruction. Phrase neutrally, balance examples across the cases the system will really see, and check whether the prompt presumes the answer it is supposed to be eliciting.

9.3Caching mechanics an architect designs around

Four decisions
DecisionRule
Cache breakpointsMark the boundary between the fixed part and the variable part, and keep the fixed part genuinely fixed
Content orderingStatic before dynamic, always. The large unchanging block first, per-request content after the breakpoint
TTL selectionMatch cache lifetime to how often the fixed content changes and how often the prompt is called. A constantly called prompt benefits from a longer life; a rare one may never amortise the write
When not to cacheWriting to the cache costs something. If a prompt is called infrequently or its fixed portion is small, caching can cost more than it saves

9.4Prompt library or Skill

Two ways to make a prompt reusable across a team. A modular prompt library is a shared collection of fragments and templates engineers assemble in their own code. A Skill is a versioned, self-contained unit, a SKILL.md packaging the instructions, optional scripts and version management, so the whole procedure travels as one governed artifact.

Which one
ConsiderationLibrarySkill
RepeatabilityAn assembled, often-tweaked prompt per useA stable procedure run the same way every time
DistributionShared within one codebase or teamAcross teams or products needing the same procedure
GovernanceLightweight, engineers own the fragmentsNeeds versioning, approval and rollback, which Skills carry
Exercise, from the module

A support organisation runs the same operation hundreds of times a day: given a ticket and the relevant manual section, draft a reply that follows the tone guidelines, cites the section it relied on, and never promises a refund or a timeline the agent has not approved. Make three decisions and justify each: where the stable prefix ends, how the never-promise rule is enforced structurally rather than as a sentence, and whether this ships as a template or a Skill.

Place your bet before the reveal

Take the third decision first. The same operation, hundreds of times a day, across the whole support organisation. Does it ship as a template or a Skill?

The model answer
DecisionAnswer
BreakpointRole, tone rules, output contract and the guardrail go first as the stable prefix. The ticket and the manual section are the only per-request content. Dynamic content before the breakpoint means the prefix changes every call and the cache never hits, and at hundreds of calls a day the prefix is where the savings live
GuardrailBuild it into the output contract as a structural constraint the format requires, not a sentence in the role text. A rule stated in the role can be drifted past. A constraint that shapes the response format cannot be quietly ignored
PackagingA versioned Skill. Stable procedure, run identically across the support org, needing versioning and rollback. A template each agent keeps locally has no central governance and drifts into slightly different versions
Same question, after the section

The support reply prompt, hundreds of times a day, and a rule that the reply never promises a refund or a timeline. Where does the never-promise rule live?

An analytics team reuses one prompt about 8,000 times a day. It opens with the customer record being analysed, then a 6,000-token block of fixed methodology and output schema. Costs are triple the projection and caching appears to do nothing.

What is the fix?

  1. Extend the cache TTL
  2. Shorten the methodology block to cut input tokens
  3. Reorder so the fixed methodology and schema come first, with the record after the breakpoint
  4. Package the prompt as a versioned Skill
Static before dynamic. This is the single most testable caching fact in the module, and the scenario telegraphs it: a large fixed block sitting behind a small variable one. At 8,000 calls a day against a 6,000-token prefix the saving is the whole point. Note what the other options are: each is a real technique that is right in a different situation, which is how distractors are built in this domain.
