Before you read

Section 5 made the claims triage assistant a workflow: Claude reads the claim, a rule engine sets priority, coverage is fetched live, Claude drafts the adjuster's email, a person approves above the threshold. Which of the five reference architectures do you adapt?

Locked in. The section will not tell you whether you were right until the end.

Patterns give you the shape. Reference architectures give you the wiring: documented ways to assemble an LLM application for a recurring class of problem, already proven in the Claude ecosystem.

They are references, not blueprints. The goal is not to match a problem to a fixed design and implement it as drawn. Every partner workload is different, so understand each shape well enough to generalise from it, adapt the one that fits, and recognise when a problem draws on more than one.

Five shapes, what good looks like, and where projects go wrong
ArchitectureGoodWrong
Agent The model works toward a goal, choosing which tools to call and in what order. Autonomy bounded by what the tools can do and a cap on turns. For paths that cannot be written in advance: investigating a codebase, multi-source research, complex case triage Unbounded autonomy. State-changing tools with no human review, no turn limit, and no measure of whether the goal was met
Retrieval-augmented generation A stable corpus, manuals, internal docs, regulatory text, is chunked and indexed. The most relevant chunks are retrieved per question and passed as context Using it for live state: order status, inventory, ticket queues. The index is a snapshot; if the data moved, the answer is wrong
Document processing pipeline (evaluator-optimizer) Structured extraction from semi-structured documents. OCR, extract against a schema, validate, route exceptions. An evaluator pass because first-pass extraction on edge cases is not trustworthy alone No exception path. Low-confidence extractions flow through the same pipeline as clean ones, with no human gate
Customer service and ticket triage (routing) Classify the intent, then route: retrieval for documentation questions, a transactional API for live state, a human approval layer for high-consequence actions Retrieval for live order status instead of the API. No escalation path. Deploying an agent variant before the simpler routed workflow has been measured
Coding agent Two phases. Agentic investigation of the codebase, because that path cannot be scripted. Then deterministic edit steps: parse, plan, propose, test, review. Subagents take isolated tasks with enough context and no more Letting it edit and commit with no human review gate. Not tracking regression rates per language or framework. Treating it as a conversation rather than a pipeline with defined handoffs

6.1When a problem needs two

Real problems often sit at a boundary. A routing workflow hands some intents to an agentic investigation loop. A document pipeline reaches for RAG over policy text on an exception. Combining is sometimes right. What matters is why you are reaching for the second one.

Reach for a second pattern when the two parts of your problem break in different ways that are worth managing separately. If you are reaching for a second pattern because you have not decided what problem you are solving, adapt a single one instead. That is a decision you are deferring, not a pattern you are applying.

6.2The mistake the module calls the most common

Place your bet before the reveal

Five shapes, each with a Wrong column. The module singles out one mistake as the most common across all of them. Which is it?

Retrieval used where a tool call belongs. This one is worth over-learning, because it is the highest-frequency distractor shape in this whole domain.

Why it broke, four ways
The errorWhat it means
A category errorRetrieval is the mechanism for knowledge: FAQs, policies, manuals. It is the wrong mechanism for transactional state
A data-architecture failure, not a retrieval failureLive state had been represented as historical text snapshots in the first place
Similarity is not truthA higher similarity score means the text was semantically close to the query. That is not the same as current
The fix is a tool callNot a better chunker, a shorter refresh interval, or a higher threshold. The knowledge base keeps the FAQs; the transactional database keeps the orders
The sentence to memorise

Retrieval is for stable knowledge: things that were true yesterday and will be true tomorrow. Tool use is for live state: things whose current value is owned by a system and changes independently of your index. Any scenario mentioning balances, inventory, status or availability is testing this.

Same question, after the section

The claims triage assistant, a workflow: Claude reads the claim, a rule engine sets priority, coverage is fetched live, Claude drafts the email, a person approves above the threshold. Which of the five reference architectures do you adapt?

A draft customer-service architecture: (1) an intent classifier, a Claude call, then two branches, (2) retrieval over an Order Status Index and (3) retrieval over a Product Manual Corpus, feeding into (4) an agent loop with tools for refund, cancel and update-address, with (5) no escalation path to a human, and (6) a response composer.

Which two components are misapplied for this design?

  1. Component 2, retrieval over the Order Status Index
  2. Component 3, retrieval over the Product Manual Corpus
  3. Components 4 and 5 together, an agent holding refund and cancel with no escalation
  4. Component 1, the intent classifier
The order-status index and the ungated agent loop. Two different failures in one diagram, which is how these items are usually built. One is a mechanism error: retrieval on live state. The other is a delegation error: irreversible actions granted to the pattern with the weakest guarantees. Fix the first with a tool call against the order service, the second with a human approval layer on anything that moves money.
