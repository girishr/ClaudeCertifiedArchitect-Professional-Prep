Pattern Selection

One page. What to build, and the constraint that decides it.

Solution Design & Architecture 17% of the exam Print me

The decision, in one line

Pick the least complex architecture that clears the binding constraint. Anthropic's stated position: start with a single augmented LLM call, add complexity only when simpler solutions demonstrably underperform.

The line the exam tests

Workflow or agent is decided by predictability of the path, not difficulty of the task. A hard task with a fixed sequence is still a workflow.

The six patterns

All six are workflows except the last
PatternUse whenDo not use when
Prompt chaining Fixed subtasks in sequence. Trading latency for accuracy. You want a programmatic gate between steps Subtasks unknown ahead. Tight latency budget. A single call already passes eval
Routing Distinct input categories handled better separately, and classification is accurate. Cheap model for easy cases Categories blur, so misroutes poison everything downstream. One prompt handles all cases without loss
Parallelisation: sectioning Independent subtasks run concurrently for wall clock. Guardrail call alongside the main call Subtasks depend on each other's output. That is chaining
Parallelisation: voting Multiple perspectives raise confidence. False negatives are expensive: security review, content safety Cost sensitive. Or one objectively correct answer a single call already gets
Orchestrator-workers You cannot predict the subtasks. Decomposition depends on the input itself Subtask set is fixed and known. Use sectioning, which is cheaper and skips the planner hop
Evaluator-optimizer Clear articulable criteria exist and iteration measurably improves output Criteria vague or subjective. Model cannot tell good from bad here. Latency forbids rounds
Autonomous agent Open-ended, step count unpredictable, model acts on environment feedback in a loop Path can be hardcoded. Failures costly and irreversible. You cannot sandbox or checkpoint
Favourite exam trap

Sectioning vs orchestrator-workers. Sectioning: you decide the split, in code, before runtime. Orchestrator-workers: the model decides the split, at runtime, from the input. If the scenario tells you the subtasks, it is sectioning and the orchestrator is overbuilt.

Multi-agent economics

Numbers from Anthropic's multi-agent research system. Carry these.

Single agent token use~4x a chat interaction
Multi-agent token use~15x a chat interaction
Lead Opus + Sonnet subagents vs single-agent Opus90.2% better on an internal breadth-first research eval
Subagents spawned in parallel, typically3 to 5
Subagent returns1,000 to 2,000 tokens after burning tens of thousands

Multi-agent wins on breadth-first tasks with heavy parallelism, where information exceeds one context window and value per task is high. Multi-agent loses on shared context, tight interdependencies, real-time coordination, and most coding work, where agents cannot see each other's edits.

Reliability, checkpoints, the human

  • Human checkpoints go at irreversible or high blast-radius actions. Money movement, production writes, external communications, permanent deletions. Not at every step, which destroys the efficiency case you sold.
  • Resumable checkpointing beats restart-from-scratch. Persist the plan to external memory so a truncated context window does not lose the task.
  • Pair model adaptability with deterministic safeguards: retries, timeouts, circuit breakers, regular checkpoints. Telling the agent a tool is failing and letting it adapt works surprisingly well.
  • Rainbow deployments shift traffic gradually so long-running agents are not killed mid-run by a deploy.
  • Guardrail calls run in parallel with the main call, not serially, when latency matters.
  • Instrument decision patterns and interaction structure, not just final outputs. Non-determinism makes output-only logs useless for debugging.

Reading a scenario

  1. Read the last sentence first. The ask is narrower than the setup.
  2. Find the binding constraint: latency SLA, compliance regime, budget, team maturity, volume, reversibility.
  3. Ask: is the path predictable? If yes, workflow. Stop escalating.
  4. If two answers both look right, one is right under a slightly different constraint. Work out which constraint separates them.
  5. Watch for absolutes. "Always" and "never" are usually wrong in a domain of tradeoffs, unless the absolute is a hard compliance rule.
