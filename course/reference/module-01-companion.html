NewThree things our track missed entirely

I built our seven lessons from Anthropic's published learning objectives before the module was readable. Most of it holds. Three pieces were not visible from the objectives and are not in our lessons at all.

1. The four properties you design around (S02)

The module opens by naming four properties of the model and treating each as a force to design around rather than a defect to fix, the way a structural engineer designs around the properties of a material. Each is presented as a capability, its matching limitation, and the mitigation.

PropertyThe design consequence to carry
Non-determinismThe same input can produce different output. Anything that must be identical every time belongs in code, and anything probabilistic needs a validation layer rather than trust
Context as a finite resourceThe window is a budget you spend, not a container you fill. More context is not free, and this is what makes context strategy an architecture decision rather than a tuning detail
Confidence is not validityFluent and wrong looks identical to fluent and right. Self-reported confidence is not a quality signal, which kills a whole family of plausible designs that route on it
Knowledge and capability boundariesThe model does not know what it was never given. Retrieval, tools and grounding exist to move a task inside the boundary

This framing is worth adopting because it explains why later answers are right. A guardrail is not bureaucracy, it is the mitigation for confidence-is-not-validity. A deterministic check in code is the mitigation for non-determinism.

2. Seven primitives, not six patterns (S05)

Our lessons went straight to the six workflow patterns. The module first inventories the parts you assemble from, which is a different and more useful level: Tools, MCP, Subagents, Hooks, Skills, Agent Teams and Dynamic Workflows, one job each.

Patterns are how you arrange primitives. Being able to name the primitive a scenario needs is a distinct skill from naming the pattern, and the checkpoint "Match the primitive to the job" tests exactly that.

3. Prompting as architecture (S24 to S27)

A whole section with no equivalent in our track. It treats prompts as durable assets rather than text you write once: system-prompt architecture for enterprise reuse, templates that enforce consistency and safety, technique selection by task complexity, behavioural differences across models, caching mechanics, and the decision between a modular prompt library and a versioned Skill.

That last one is a genuine architecture call and reads like exam material: when does reusable prompt content become a Skill rather than a library entry.

The one to memorise

Retrieval applied to live state. The module calls this the most common mistake. If a scenario needs the current value of something, that is a tool call against the system of record. RAG answers from a corpus that was true when it was indexed. Any question involving balances, inventory, status or availability is testing this.

RecapThe module's own five takeaways

From the closing screen, in the course's own framing. If you remember nothing else, these five.

  1. Decomposition comes before architecture. Split the work first, then pick a shape.
  2. Choosing a pattern is choosing how much autonomy to grant. Not how clever the solution is.
  3. Reach for a tested reference architecture before inventing one. The industry has already paid to learn these.
  4. Start with Sonnet and treat every model swap as a release. Gate it with an eval before it ships.
  5. Pick the entry point by the work it has to do, not by what is already on the shelf.

Notice how much of this is restraint. Decompose before designing, use the known shape, start at the middle tier, choose by the work. The module's editorial position is the same as the engineering blog's: complexity has to earn its place.
