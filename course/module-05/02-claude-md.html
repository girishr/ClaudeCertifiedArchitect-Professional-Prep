The CLAUDE.md hierarchy

Four scopes, all concatenated rather than overriding, and a context budget you spend whether you meant to or not.

Two things go wrong with CLAUDE.md on real teams, and both are decisions rather than accidents. The first is putting a rule in it that had to be guaranteed, which section 3 deals with. The second is treating it as documentation: everything anyone might need, imported from three other files, four hundred lines long, contradicting itself in two places. That version loads on every single turn and gets followed less than the short one did.

So the decision here is scope and size. Which of the four files does this belong in, and does it belong in a file that is always in context at all.

Managed policy CLAUDE.md cannot be excluded. Everything else can be filtered out with claudeMdExcludes globs. If you would rather not ship a file to every machine, claudeMd inside managed-settings.json does the same job from the policy file.

2.1Imports, and what they do not save you

@path imports expand at launch, relative to the importing file, to a maximum depth of four hops. An import written inside backticks or a fenced code block is not followed, which is how you show an example of one without triggering it.

Watch out

Importing a large document into CLAUDE.md does not reduce context cost. The import expands at launch and you pay for every token of it on every turn, exactly as if you had pasted it in. Imports are an organisation device for the humans editing the file, nothing more. The two mechanisms that genuinely keep content out of context until it is needed are path-scoped rules and Skills.

Three practical rules hold across all of them. Keep each file under 200 lines, because longer files reduce adherence rather than increasing it. Be concrete: "use 2-space indentation" is a rule, "format properly" is a wish. And remove contradictions rather than ranking them, since nothing in this hierarchy overrides anything and Claude may pick either side of a conflict.

Watch out

Project-root CLAUDE.md is re-injected after /compact. Nested and path-scoped rules are not. So a long session that has compacted once is still following the root file and may no longer be following the rule that covered the directory it is working in. If a constraint must hold for the whole of a long session, the root file is where it survives.

Treat CLAUDE.md as the shortest possible answer to "what would I tell a competent new joiner on day one", put anything narrower behind a paths: rule, and put anything that must not be editable somewhere else entirely.
