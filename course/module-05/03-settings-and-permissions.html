Settings and permissions precedence

Five ranks, and one step in the order that is the inverse of what habit tells you.

Exam domain 7From this kit's domain notes
CCAR-P course / Module 5 / Section 03 of 7

The requirement usually arrives in one sentence from someone in security. Nobody reads .env. Nothing runs terraform apply outside the pipeline. The interesting part is never which rule to write, it is where to write it so that it still applies when an engineer edits the repo, passes their own flags, or keeps a personal settings file with different ideas.

That makes the precedence order the examinable thing in this section, and one step of it is genuinely surprising.

3.1Writing the rules

Rules live under permissions as allow, ask and deny, and the syntax names a tool and a pattern: Bash(npm run test *), Read(./.env). Pattern matching is more literal than it looks, and the whitespace is load-bearing.

The space before the wildcard changes what the rule catches
RuleWhat it matches
Bash(git diff *)A prefix match on git diff followed by arguments
Bash(git diff*)The same, and also git diff-index and anything else beginning with those characters

Which way round you want depends on the rule. In an allow list the loose form quietly permits commands you did not consider; in a deny list the loose form is often exactly what you want. Read your own wildcards in both directions before you ship them.

3.2Taking the choice away

Two managed-only controls exist for the case where the floor has to be a floor. allowManagedPermissionRulesOnly stops user and project settings from defining any permission rules at all, so the managed set is the whole set. allowedMcpServers and deniedMcpServers do the equivalent job for which MCP servers may be connected at all, at org level.

Underneath all of it is one division of labour worth stating flatly, because it decides a large share of this domain's questions: enforcement belongs in settings, behavioural guidance belongs in CLAUDE.md. The two are not interchangeable and neither one substitutes for the other.

Watch out

Two placements look like policy and are not. A rule in the committed project CLAUDE.md is advisory: it is context, and any contributor can edit it in a pull request. A rule in .claude/settings.local.json is real enforcement but personal: the file is gitignored, so it protects you and nobody else. Team standards go in the committed .claude/settings.json; standards nobody may opt out of go in managed settings.

A payments company runs Claude Code across nine repositories. Security has one non-negotiable: no session may read .env files, on any machine, in any repo. The engineers are experienced, they pass their own flags routinely, several keep personal settings files with relaxed rules, and all nine repos are open to internal contributors who can edit any committed file through review.

Where does the rule go?

  1. A permissions.deny rule for Read(./.env) in each repo's committed .claude/settings.json, with the reason documented in CLAUDE.md
  2. A permissions.deny rule in managed-settings.json on every machine, with allowManagedPermissionRulesOnly set
  3. A PreToolUse hook in each repo's .claude/ that inspects the tool call and exits 2 on any path ending in .env
  4. A prominent instruction never to read .env at the top of the managed policy CLAUDE.md, which cannot be excluded
Managed settings, rank 1. Three constraints in the stem eliminate everything else: engineers pass their own flags, which kills anything below rank 2; personal settings files exist, which kills rank 4; and contributors can edit committed files, which kills any repo-resident mechanism including the hook. Option D is the trap in its strongest form, because the managed policy file really is unexcludable, and it is still only context.

When a requirement has the word "must" in it and a named person who will be asked why it failed, work down from rank 1 rather than up from the repo.
