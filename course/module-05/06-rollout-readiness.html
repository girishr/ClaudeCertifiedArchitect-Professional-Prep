Rollout and operational readiness

The order you standardise a team in, and what you can still prove about a run six weeks later.

Exam domain 7From this kit's domain notes
CCAR-P course / Module 5 / Section 06 of 7

Rollout questions in this domain almost always turn on sequence. Someone proposes building the team a plugin on day one, or shipping managed settings before anyone has agreed what the conventions are. Both are the right mechanisms in the wrong order, and the cost is that you are now distributing a standard nobody has used yet.

The order below works because each step assumes the one above it exists and has been lived with for a while.

Standardise in this order
#What you addWhy here and not earlier
1A committed project CLAUDE.md. /init bootstraps a first draft, /doctor proposes trimsThe conventions have to be written down before anything can enforce them, and writing them reveals which ones the team does not actually agree on
2.claude/settings.json with a shared allow and deny baselineNow that the conventions exist, the subset that is not negotiable can be moved from prose into enforcement, in the committed file the whole team shares
3.claude/agents/ with the roles the team keeps recreating by hand, typically a reviewer and an explorerYou only know which roles are worth defining after people have delegated the same work a few times. In the repo, so they are shared and reviewable
4Hooks for the non-negotiables: format on write, block secret reads, run lintBy now you know which rules people forget, and those are precisely the ones that should stop depending on anyone remembering
5Package the lot as a plugin, distributed through a private marketplaceOnly once more than one repository needs the same setup. Before that, the plugin is versioning overhead around a single directory

Underneath all five, managed settings and a managed CLAUDE.md provide the org-wide floor that individuals cannot override. That floor is a separate decision from the rollout, not the last step of it: it exists because someone outside the team requires it, and it is deliberately not the team's to change.

Two naming details once plugins are in play. Plugin skills are namespaced as /plugin-name:skill-name, so two plugins can ship a skill with the same short name. And a project or user agent overrides a same-named plugin agent, which is how one team adjusts a distributed definition without forking the plugin.

6.1What you can prove afterwards

The handover question a security reviewer asks is not "is it configured correctly" but "show me what actually loaded on that run". Six things answer it.

Reproducibility and audit
ToolWhat it establishes
--bare in CIThat the run did not depend on the repo's hooks, the runner's home directory, or anyone's local configuration
/contextWhat is actually in context right now, which is how you catch an instruction file you assumed was loaded and is not
/statusWhich setting sources are in play, which is the fastest way to explain a precedence surprise
InstructionsLoaded hooksA logged record of instruction provenance, per session, rather than a reconstruction after the fact
--output-format jsonCost and session id captured per run, so a given output can be traced back to the run that produced it
CLAUDE_CODE_ENABLE_TELEMETRYFleet-level metrics, for the adoption and spend questions that arrive a quarter later
Watch out

Auto memory is not a team artefact. It is machine-local, Claude-authored and unversioned, so it is not shared across machines, not reviewable, and not something a colleague inherits. Any proposal that uses it as the team knowledge base is wrong for three independent reasons. Team knowledge goes in the committed CLAUDE.md, in path-scoped rules, or in a Skill.

What you hand over, then, is a repository whose .claude/ directory explains itself, a short list of things that are enforced rather than suggested, and a CI step that produces the same result no matter who triggered it.
