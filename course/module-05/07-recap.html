The six takeaways
#TakeawayThe operative detail
01Some mechanisms enforce and some only suggestCLAUDE.md, Skills and MCP servers are context and capability: they shape behaviour without guaranteeing it. Hooks, permission rules and a subagent's tool allowlist are enforcement. Read the strength of the obligation in the stem before you read the options
02Managed settings outrank command-line argumentsThe order is managed, CLI args, local, project, user. That top pair is the inverse of how most tooling behaves and it is the likeliest single item in the domain
03The CLAUDE.md scopes concatenate, they do not overrideManaged policy, user, project, local, all loaded, closest to cwd read last. So a contradiction between two of them is a defect to remove, not a precedence question to reason about
04Only two things keep content out of context until neededPath-scoped rules in .claude/rules/ and Skills. Imports are organisation for the humans: they expand at launch and cost the same tokens as pasting the text in
05Reproducibility in CI is a flag, not a convention--bare plus an explicit --allowedTools. Without it the run executes the repo's hooks, connects its .mcp.json servers, and inherits the runner's home directory
06Standardise in order, and keep the org floor separateCLAUDE.md, then shared settings, then agents, then hooks, then a plugin once a second repo needs it. Managed settings and a managed CLAUDE.md are a different decision, made by someone outside the team

7.2Common distractors

Each of these is a real mechanism offered for the wrong requirement
The optionWhy it fails
Put the security policy in the project CLAUDE.mdA committed CLAUDE.md is advisory and any contributor can edit it. Use managed settings permissions.deny
Use a PostToolUse hook to prevent a dangerous commandToo late. PostToolUse cannot block. PreToolUse can
Rely on .claude/settings.local.json for team standardsIt is gitignored and personal. It protects you and nobody else
Give every engineer their own subagents in ~/.claude/agents/Not shared and not reviewable. Use .claude/agents/ in the repo
Assume CLI flags beat managed settingsThey do not. Managed settings sit above command-line arguments
Import a large document into CLAUDE.md to organise itImports expand fully at launch and cost the same context. Path-scoped rules and Skills reduce context; imports do not
Expect a subagent to know what the main thread just discussedIt gets CLAUDE.md and a git status snapshot, not the conversation. Only a fork inherits that
Run claude -p in CI without --bare and expect reproducibilityIt picks up the repo's hooks, its .mcp.json, and the runner's ~/.claude
Use auto memory as the team knowledge baseMachine-local, Claude-authored and unversioned. Not a team artefact at all

7.3Closed-book self-test

Six questions, no scrolling. This domain is recall, so a hesitation is a real signal: anything that does not come out cleanly is one list to reread, not a section to redo.

  1. State the settings precedence from highest to lowest, all five ranks, and name the pair whose order is counter-intuitive.
  2. State the four CLAUDE.md scopes in load order. Do later ones override earlier ones? Which single file is re-injected after /compact, and which are not? Which scope cannot be excluded, and what handles excluding the rest?
  3. Which hook events can block, which one notoriously cannot, and what does exit code 2 do when the JSON output says permissionDecision: "allow"?
  4. Name the three MCP scopes with their precedence order, and say what a claude -p run does with a project .mcp.json that an interactive session would have prompted about.
  5. What does --bare skip, why is it the CI recommendation, and what credential does it require?
  6. Give the five-step standardisation order for a team, and name the two artefacts that put a floor under it which individuals cannot override.

If those came easily, two more worth having: the subagent precedence order and what a subagent inherits versus what a fork inherits; and the difference between Bash(git diff *) and Bash(git diff*).

7.4What this buys on the exam

Domain 7, Developer Productivity and Operational Enablement, is 7 percent of the paper. About four questions, and they are the most mechanically answerable four on it: if the lists above are solid, you should expect to get all of them. That is the end of the reading.

Where to go now

This is the last module in the path, so there is nothing further to read. Go back to the study hub and switch modes: the practice tab holds the question engine, and the study plan on the same page lays out the remaining evenings. Spend what is left answering questions rather than rereading pages. Work mixed-domain sets under time pressure so you practise recognising which domain a stem belongs to, which is half the difficulty of the real paper. Turn the four precedence lists from this module into flashcards and give them five minutes a day rather than another hour once. And when you get something wrong, go back only to the section the wrong answer traces to. Modules 1 and 2 are 65 percent of the paper between them, so if a review pass has to be rationed, that is where it goes. Do not spend it here.
