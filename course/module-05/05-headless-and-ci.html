Headless runs and CI

Making a non-interactive run give the same answer on every machine, and knowing what it picks up when you do not.

Exam domain 7From this kit's domain notes
CCAR-P course / Module 5 / Section 05 of 7

A headless run in CI has a property interactive use does not: nobody is watching, and nobody is there to answer a prompt. Which means two things stop being conveniences and become correctness problems. Whatever the run discovers on disk, it uses. Whatever it cannot get permission for, it either does silently or fails silently.

The reproducibility question is the one the exam asks. A pipeline step that behaves differently depending on whose laptop image the runner was built from is not a pipeline step.

5.1The flags that decide the run

What each one settles
FlagWhat it does
claude -p "prompt"The non-interactive run itself. Exit 0 on success, non-zero on failure, so the shell semantics a pipeline expects are already there
--bareSkips auto-discovery of hooks, skills, plugins, MCP servers, auto memory and CLAUDE.md. The recommended mode for CI and scripts, and slated to become the -p default. Needs ANTHROPIC_API_KEY, not a subscription login
--output-format text | json | stream-jsonjson carries total_cost_usd and per-model cost, which are client-side estimates rather than billed figures, plus the session id
--json-schemaAdds a validated structured_output field, for when a later step has to parse the result rather than a human read it
--allowedTools "Bash,Read,Edit"The explicit tool allowlist. In CI, write it out rather than inheriting whatever the environment had
--permission-mode dontAskLocked-down CI: denies anything that is not explicitly allowed or read-only, instead of hanging on a prompt nobody can answer. acceptEdits is the looser choice for lint-fix style jobs
--append-system-promptPer-run role framing, for example the same repo reviewed as a security reviewer in one job and a docs reviewer in another
--continue and --resume <session_id>Multi-step pipelines that need the earlier steps' context rather than a fresh start each time

5.2Why --bare is the answer to a reproducibility question

Without it, a -p run in an untrusted folder still executes that repo's hooks and connects its .mcp.json servers, because there is no trust dialog in the headless path to ask about it. It also picks up the runner's ~/.claude. So the result depends on the repo you checked out and the image the runner came from, which is the definition of a flaky step.

Watch out

"A team member's local configuration could change the CI result" is not a vague worry, it is the argument for --bare, and it is how this item tends to be worded. If a stem mentions inconsistent CI behaviour across machines or runners, --bare plus an explicit tool allowlist is the shape of the answer. Remember that bare mode also gives up CLAUDE.md, so anything the run genuinely needs to know has to arrive through the prompt, --append-system-prompt, or an explicitly passed setting source.

5.3Failing the build for the right reason

A run whose plugin failed to load, or whose MCP server never connected, can still exit 0 having done less than you asked. The system/init event carries plugin_errors and mcp_server_errors: check them and fail the build on a non-empty list, rather than discovering weeks later that a gate has been a no-op.

One operational limit worth remembering because it turns into a mysterious truncation: piped stdin caps at 10MB. Anything larger goes to a file, and you pass the path.

For CI, the default to reach for is --bare, an explicit --allowedTools, --permission-mode dontAsk, --output-format json captured as a build artefact, and a check on the init event's error lists.
