Six ways to extend a session, and the only column that decides between them is whether the behaviour is guaranteed.

Given a requirement, pick the mechanism. That is the whole exercise, and the tempting answers are all real mechanisms used slightly early or slightly late: a Skill for something that had to happen every time, a hook for something that was only a convention, a fresh subagent for work that needed the conversation it came from.

Read the Enforces column first and the Use for column second. A requirement phrased as an obligation has exactly two homes in this table, and the other four rows are distractors no matter how well they fit the description of the work.

4.1Subagents, and the one thing they do not inherit

A subagent starts fresh. It receives CLAUDE.md and a git status snapshot. It does not receive the conversation history, the output style, or the main thread's auto memory. So a subagent cannot act on something you established three turns ago unless you restate it in the delegation.

The exception is a fork, via /subtask, which inherits the full conversation and shares the parent's prompt cache. When you need the current context in a side task, that is the mechanism. When you want the context kept out, use a subagent.

Subagent definitions resolve in their own precedence order: managed settings, the --agents flag, .claude/agents/, ~/.claude/agents/, then plugin agents/. Project and user agents override a same-named plugin agent, which is how a team adjusts a distributed definition without forking the plugin.

Frontmatter worth recognising in a stem. name, description (this is what drives auto-delegation, and "use proactively" in it makes delegation more likely), tools and disallowedTools, model including inherit, permissionMode, maxTurns, memory, skills, isolation: worktree, and effort.

4.2Hooks: where they fire and which ones can stop you

The events, grouped by whether they can block
EventCan blockReach for it when
PreToolUseYesA specific tool call must be prevented before it runs. The only correct place for a veto
UserPromptSubmitYesA prompt must be checked, enriched or refused before the model sees it
Stop, SubagentStopYesThe session or subagent should not be allowed to finish yet, for example with a check unmet
PreCompactYesSomething must be preserved or recorded before context is compacted away
PostToolUseNoReacting after the call has already happened: format the file just written, log it, run a test
SessionStart, SessionEndNoSetting up or tearing down around a session, and emitting a record of it
SubagentStart, PostCompactNoRe-establishing state after a boundary the session just crossed
PermissionRequestIt decidesAnswering a permission prompt programmatically, with permissionDecision
InstructionsLoadedNoLogging which instruction files actually loaded. The debugging and audit hook
ConfigChangeNoReacting when configuration changes during a session

Exit codes carry the semantics. Exit 0 succeeds. Exit 2 blocks, and it beats a JSON permissionDecision: "allow". Other codes are non-blocking unless the JSON says otherwise. JSON control lives under hookSpecificOutput, where permissionDecision takes allow, deny or ask.

Watch out

A PostToolUse hook cannot prevent anything. If a stem describes stopping a dangerous command and an option offers PostToolUse, the option is wrong by timing alone, however good the logic inside the hook is. The same goes for a subagent expected to know what the main thread just discussed: it does not, unless it is a fork.

4.3MCP scopes

Three scopes, and who ends up with the server
ScopeStored inWho gets it
local, the default~/.claude.jsonYou, in this project only
project.mcp.json, committedThe whole team, through the repo
userYour user configYou, across all your projects

Precedence runs local, project, user, plugin, then claude.ai connectors.

Watch out

Project servers prompt for approval interactively, so an engineer opening an unfamiliar repo gets asked. claude -p, the Agent SDK and cloud sessions do not ask: there is no trust dialog in those paths, and the repo's .mcp.json servers are connected. If a particular server must not load in those contexts, keep it out explicitly with disabledMcpjsonServers or --setting-sources, and see section 5 for the blunter instrument.

Work from the obligation backwards. Must happen every time: a hook, or a permission rule. Should be followed: CLAUDE.md, or a path-scoped rule. Occasionally invoked and multi-step: a Skill. Verbose work where you only want the conclusion: a subagent. Needs what was just said: a fork.
