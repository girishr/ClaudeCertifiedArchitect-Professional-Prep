Tool design and capability bloat

What makes a tool Claude uses correctly, and what to do when there are more tools than the context window can afford.

Exam domain 3From this kit's domain notes
CCAR-P course / Module 2 / Section 04 of 12

When the model calls the wrong tool, or calls the right tool with wrong arguments, the instinct is to edit the system prompt. That is almost always the third-best fix. The tool description and the error string are the two things the model reads at the moment it makes the mistake, and they are the two things you control most directly.

Anthropic attributes Sonnet 3.5's SWE-bench Verified result largely to refined tool descriptions. That is the weight to put on this: description quality matters more than anything else you control at this layer.

4.1Descriptions, names and namespaces

Write the description as you would for a new engineer joining the team: what the tool does, when to use it, when not to use it, how its resources relate to each other, and any niche query syntax it expects. The "when not to" clause is the one people omit and the one that stops wrong selection.

4.2Return something the model can use, at a size it can afford

A tool that returns raw records forces the model to guess what they mean. Resolving UUIDs to names reduces hallucination in retrieval tasks, which is a cheap change with a measured effect.

4.3Errors are prompts, and annotations are not guarantees

There are two error channels and they behave differently.

The two error channels
ChannelUsed forWhat the model can do
JSON-RPC protocol errorsUnknown tool, malformed requestUsually nothing. These are your bug, not the model's
Tool execution errors, returned as a normal result with isError: trueBad argument, business-rule violation, upstream failureSelf-correct, if the text is actionable. Clients SHOULD feed these back to the model

So put the useful sentence in the second channel. "Invalid departure date: must be in the future. Current date is 08/08/2025." tells the model what to change. "Validation error" does not.

Watch out

The annotations readOnlyHint, destructiveHint, idempotentHint and openWorldHint are hints for UI and policy. Clients MUST treat them as untrusted when they come from an untrusted server. Setting idempotentHint: true does not make retries safe; server-side idempotency keys do. Any answer that treats an annotation as behaviour is wrong.

4.4Capability bloat, and the ladder out of it

Bloat has measurable symptoms, and they are the numbers a scenario will hand you as its constraint.

  • Selection accuracy degrades past roughly 30 to 50 tools.
  • A five-server setup (GitHub, Slack, Sentry, Grafana, Splunk) burns about 55k tokens on definitions before reading the user's first message.
  • Naive multi-server hosts can spend about 150k tokens on definitions alone.

Watch out

The caching interaction is a favourite trap. Providers cache the prompt prefix including the tools array, so adding or removing definitions mid conversation invalidates the cache, and the miss can cost more than the definitions you saved. Mitigations: append discovered definitions after the cache breakpoint, or route everything through a stable call_tool({name, args}) meta-tool, and treat a server disconnection as a conversation boundary. On the Anthropic API, defer_loading: true plus cache_control on the same tool is a 400.

The order is the answer to most bloat questions: consolidate at design time, split by domain where ownership differs, and only then defer loading and add search. If the task chains tools with large intermediates, go straight to programmatic calling in a sandbox, because no amount of description tuning fixes 100k tokens of intermediate payloads passing through the context window.
