MCP in depth

The participants, the two layers, the primitives, and the four things you probably still believe that the spec has dropped.

Exam domain 3From this kit's domain notes
CCAR-P course / Module 2 / Section 03 of 12

Section 2 decided that this capability wants MCP. This section is what you are committing to when you say that, and it matters more than usual because MCP has moved. The spec revision to hold in mind is 2026-07-28, and several features that older exam guides still teach as live are deprecated in it. A distractor built from a deprecated feature is the hardest kind to reject, because it sounds like something you read.

3.1Participants and layers

The host is the AI application. It creates one client per server, and each client holds its own dedicated connection. "Local" and "remote" describe where the server runs, not two different protocols. Local stdio servers typically serve one client; remote HTTP servers serve many.

The two transports
TransportShapeWhat to remember
stdioNewline-delimited JSON-RPC over a client-launched subprocessCredentials come from the environment, not OAuth. A one-click install MUST show the exact command and get explicit consent
Streamable HTTPEach message is an HTTP POST to one MCP endpoint; the reply is JSON or a request-scoped SSE streamBearer token on every request. Never put tokens in the query string

3.2Primitives, and who controls each

The control column is the examinable part. Which party decides that a given primitive gets used is what separates a tool from a resource from a prompt.

Primitives and their controller
PrimitiveSideControlled byNotes
ToolsServerThe modelThe model decides when to call one. tools/list, tools/call
ResourcesServerThe applicationRead-only, URI-addressed, direct or templated. resources/list, resources/read
PromptsServerThe userTemplates, typically surfaced as slash commands. prompts/list, prompts/get
ElicitationClientThe server asks, the user answerselicitation/create, for a confirmation or a missing value mid-call. The surviving client-facing feature
Watch out

When the model needs a confirmation or a value it does not have part way through a call, the answer is elicitation. Not guessing a default, and not adding a second tool whose only job is to ask.

3.3The deltas that make distractors

Every row here is something a plausible option will assert. Learn them as rejections.

What changed in spec revision 2026-07-28
The stale beliefThe current position
"Use MCP sampling so the server stays model-agnostic"Sampling, Roots and Logging are all deprecated, along with the legacy HTTP+SSE transport, on a twelve-month minimum deprecation window. Integrate with the provider directly. Elicitation is the surviving client-facing feature
"Use the server-to-client logging utility for observability"Logging is deprecated. Log to stderr on stdio, or use OpenTelemetry
"The connection opens with an initialize handshake and holds a session"MCP is stateless. No initialize, no protocol-level session. Every request carries the protocol version and client capabilities in _meta, and servers advertise through server/discover
"Cache hints live on server/discover"ttlMs and cacheScope are documented on the list responses, meaning tools/list, prompts/list and resources/list, not on server/discover itself
"The server keeps per-connection state for me"Server state uses explicit handles returned from a creation tool and passed back as an ordinary argument. A handle is a name, not a capability: bind it server-side to the authenticated user and validate it on every call
"The server pushes tool-list changes, so polling is unnecessary"Change notifications are opt-in. The client opens subscriptions/listen naming the types it wants, and the server then sends notifications/tools/list_changed. Best-effort, so still poll
"Hold the connection open for the long-running job"The Tasks extension returns a durable handle instead

3.4Connectors and the MCP connector are not the same thing

Two things share a name, and questions exploit it.

  • Connectors in the Claude apps are packaged remote MCP servers for end users.
  • The MCP connector on the Messages API is the API equivalent. mcp_servers supplies url, name and authorization_token, and an mcp_toolset entry in tools enables or disables individual tools through default_config plus per-tool configs, so you can allowlist or denylist without touching the server.

Its limits are the examinable part: tools only, HTTPS only, no stdio. The moment a brief needs resources or prompts, the connector is out and you need a real MCP client.

Methods worth being able to name

tools/list, tools/call, resources/list, resources/read, prompts/list, prompts/get, elicitation/create, server/discover, subscriptions/listen, notifications/tools/list_changed. The pattern is */list and */get for discovery, then a verb.

If you remember one sentence from this section, make it this: MCP in its current form is stateless, tools are model-controlled, and anything you think the client can be asked to do for the server is probably elicitation or deprecated.
