Diagnosis and optimisation

Naming the failure from its symptom, then fixing it with the cheapest lever that can reach it.

Exam domain 4From this kit's domain notes
CCAR-P course / Module 2 / Section 11 of 12

This is the page the rest of Domain 4 exists to support. Most questions in the domain are an incident report with four fixes attached, and the fixes are all real techniques. What separates them is whether they act on the layer that is actually broken. So there are two ordered lists to hold: one that names the failure, and one that spends money in the right order once you have named it.

11.1The diagnosis tree

Work it in order and stop at the first branch that fits. Skipping to step 5 because the output looks like a reasoning problem is how teams end up rewriting prompts against a retrieval bug.

Step 2 has three distinct answers and they need three different fixes, so it is worth separating them explicitly.

11.2Fast discriminators

Often the scenario gives you the discriminator instead of the diagnosis, and expects you to convert. This table is the conversion.

Symptom to failure mode
The symptom in the scenarioThe failure it names
Varies with how the question is phrasedPrompt problem
Varies with the query but not with the promptRetrieval problem
Error-rate spike in one spanTool problem
Stable across every prompt you tryCapability problem
Correlates with conversation length or input sizeContext problem

An internal research assistant answers questions over 40,000 policy documents. Users report that about 8% of answers cite a clause that does not exist in the document the answer names. The team measures recall@20 against their labelled query-to-chunk set at 94%, unchanged since the corpus expansion three months ago. Tool error rates are flat. The behaviour appears at the same rate however the question is phrased.

What is the correct next change?

  1. Rebuild the index with a larger embedding model and raise top-K from 20 to 50
  2. Require the answer to quote the supporting passage, allow "I do not know", and penalise unsupported claims in the eval
  3. Move the assistant to a higher model tier
  4. Add ten few-shot examples of well-formed answers to the system prompt
Recall is healthy, so the index is exonerated. Phrasing independence rules out a plain prompt-clarity problem and tempts you towards capability, but the tree puts hallucination before capability for a reason: the facts were present and the model asserted something else. Grounding is the cheapest lever that can reach it.

11.3The optimisation ladder

Once the failure is named, the fix order is fixed too. Cheapest and fastest first, and each rung down costs more to build and more to maintain.

Two details on the ladder are worth stating separately because they get asked directly. Rung 4, prompt caching: the prefix order is tools, then system, then messages, so changing tool definitions invalidates everything downstream, and the breakpoint goes on the last block that is byte-identical across requests. Up to 4 breakpoints, with a 20-block lookback. Rung 6, routing: classify first, then validate both paths on the same eval set, because a router that is right 95% of the time has a 5% failure mode you have not measured.

Watch out

Caching changes cost and TTFT, not quality. "Enable prompt caching" is never the answer to an accuracy complaint. Similarly, "raise temperature" when the complaint is inconsistency makes it worse, and "fine-tune the model" is almost never the first move.

11.4Latency is its own ladder

Engineer for quality first and optimise second. Then: reduce output tokens, using max_tokens and sentence or paragraph limits rather than word counts, which models follow poorly; pick a faster model; and stream. Remember what streaming buys. Streaming improves TTFT only, not total latency. If the constraint is a total-latency SLA, streaming does nothing for you.

The habit to leave with: name the failure before naming the fix, and when two fixes both reach the named failure, take the cheaper one and measure it.
