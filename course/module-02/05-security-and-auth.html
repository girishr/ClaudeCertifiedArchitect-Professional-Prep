Security and authentication

Who holds the token, what the token is allowed to be, and why every tool result is untrusted input.

The second recurring theme of Domain 3 is blast radius, and this is where it is tested directly. Questions here quote the spec's MUST and MUST NOT language closely, so this is one of the few places in the course where verbatim recall beats reasoning. The wrong answers are usually real security measures that are necessary but not the named requirement.

5.1OAuth 2.1 for remote MCP servers

Three roles, and mixing them up is the root of most confusion. The MCP server is the OAuth resource server. The MCP client is the OAuth client. The authorization server is a separate party. The chain runs:

  1. The client makes an unauthenticated request.
  2. The server answers 401 with WWW-Authenticate carrying resource_metadata and a scope hint.
  3. The client fetches Protected Resource Metadata (RFC 9728, which servers MUST implement).
  4. The client discovers the authorization server (RFC 8414 or OIDC Discovery).
  5. The client obtains a client ID.
  6. The client runs authorization code plus PKCE, with a resource parameter (RFC 8707) naming the canonical server URI.
  7. The client validates iss on the response (RFC 9207).
  8. The client exchanges the code, then sends Authorization: Bearer on every request.

5.2The confused deputy

This one is worth knowing as a set of conditions rather than a slogan, because scenarios describe the conditions and expect you to name the attack.

Conditions, attack, mitigation
StageDetail
Conditions, all fourAn MCP proxy uses a static client ID with a third-party authorization server; it lets MCP clients register dynamically; the third-party authorization server sets a consent cookie; and the proxy does no per-client consent
The attackAn attacker registers a client with redirect_uri: attacker.com. The victim's existing consent cookie skips the third-party consent screen, so the authorization code lands at the attacker
MitigationPer-user, per-client_id consent checked before forwarding. Exact-string redirect_uri matching with no wildcards. Single-use state stored only after consent is approved. Cookies that are __Host- prefixed, Secure, HttpOnly and SameSite=Lax
Watch out

"Add PKCE to prevent mix-up attacks" is wrong, and it is wrong in a way that rewards precision. PKCE protects the authorization code. It says nothing about which authorization server answered. Issuer validation is the stated mitigation for mix-up.

5.4Prompt injection in a tool-calling system

Treat every tool result as untrusted input, including results flowing from one server into another. That second clause is the one scenarios test: server A returns text, the model passes it to server B, and nobody validated it because it came from inside the system.

The defences that appear as correct answers:

  • Human-in-the-loop confirmation for sensitive or destructive calls.
  • Showing tool inputs before execution.
  • Allowlisting tools per agent role.
  • Least-privilege OAuth scopes.
  • Sandboxing with no direct network egress.
  • Output validation and truncation.
  • Per-call authorization even for calls originating inside an approved script. Approving a script is not blanket approval for every call it makes.
The sandbox distractor. "Sandbox the code, so the script's calls are pre-approved" merges two independent controls. The sandbox bounds what the code can reach. The broker still has to evaluate each call.

5.5Least privilege on scopes

scopes_supported should be the minimal set needed for basic function, with incremental escalation through WWW-Authenticate challenges as the client needs more. Wildcard or omnibus scopes such as * or full-access are a listed common mistake. Note that clients accumulate scopes by union when they re-authorize, so a careless escalation path quietly becomes an omnibus grant.

The one-line version of this whole section: a token belongs to exactly one server, a handle belongs to exactly one authenticated user, and a tool result belongs to nobody you trust.
