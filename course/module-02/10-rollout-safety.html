Rollout safety and regression control

Five ways to put a change in front of reality, and the four inputs you have to version separately to know which one moved.

Exam domain 4From this kit's domain notes
CCAR-P course / Module 2 / Section 10 of 12

"Quality dropped and nothing changed" is the most common incident in this domain, and it is almost always false. Something changed: a floating model alias resolved to a new version, the retrieval index was rebuilt, someone edited a tool description. The point of everything in this section is to make that sentence impossible to say.

10.1Five rollout mechanisms

They are not a ladder. Each one buys a different kind of evidence at a different price, and the scenario's constraint picks.

What each mechanism gives you, and what it costs
MechanismGives youCost or risk
Offline regression suite in CIBlocks known-bad changes pre-mergeOnly covers what you encoded
Shadow (mirror traffic, discard output)Real-distribution comparison at zero user riskDoubles inference spend, and gives no user-reaction signal
Canary (small live percentage)Real user signal with a bounded blast radiusNeeds fast rollback and per-cohort metrics
A/B testA statistically comparable effect on the KPINeeds traffic volume and a fixed stopping rule
Progressive rollout by tenantContains risk for high-value accountsSlower, more operational overhead
Watch out

Two distractors live in this table. "Ship to 100% and monitor" is what canary and shadow exist to prevent. And "A/B test it" is wrong twice over: when traffic cannot reach significance, and when a shadow run would answer the same question with no user risk at all. Read the traffic volume in the scenario before choosing A/B.

10.2Pin the version, and change one input at a time

Pin model versions in production and in CI. A floating alias is how "nothing changed but quality dropped" happens, and it is an unlogged deploy. Run the golden set on a new model version before switching, and keep the old version available for rollback.

Then treat these four as independently versioned inputs, and change one at a time while diagnosing:

  1. The prompt.
  2. The tool schemas.
  3. The retrieval index.
  4. The model version.

Log a request ID and a config hash with every eval run, so a regression can be bisected rather than argued about.

The diagnostic shortcut. Quality regressed with no repo change, so check for a floating model alias or a rebuilt retrieval index. Those are the two inputs that can move without a commit.

10.3Run large eval sets on the Batch API

Evals are the canonical batch workload: nobody is waiting, and they are large enough for the discount to matter.

Message Batches API, the numbers
PropertyValue
Price50% cheaper
Typical completionMost batches within an hour
Ceiling24 hours
SizeUp to 100,000 requests or 256 MB
StreamingNone

Those last two rows are why "use batch processing" is a wrong answer for anything interactive. No streaming and a 24-hour ceiling is disqualifying for a user-facing path, and perfectly fine for evals, backfills, moderation and bulk generation.

So the posture: pinned versions, a golden set run before the switch, one input changed at a time, and the cheapest mechanism that produces the evidence the decision actually needs. Shadow when you need distribution and no risk, canary when you need user reaction, A/B only when the traffic can carry it.
