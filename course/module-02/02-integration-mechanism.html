Choosing the integration mechanism

Six ways Claude can reach a capability, and the constraint that eliminates five of them.

Exam domain 3From this kit's domain notes
CCAR-P course / Module 2 / Section 02 of 12

The first integration question is never "should we use MCP". It is "where does this capability live, who else needs it, and what is not allowed to move". Answer those three and the mechanism is usually forced. Get them in the wrong order and you end up building an MCP server for a function two services call, or wiring a direct SDK integration into four applications that will now drift apart.

Six mechanisms, and the exam expects you to place a scenario in one of them on sight.

The six mechanisms, with the conditions that select and disqualify each
MechanismUse whenDo not use when
Direct API or SDK tool useYou own both ends, the tool set is small and stable, and you want tight control over schemas and latencyThe same tools must be reusable across many hosts, or a third party supplies the capability
MCP server, local (stdio)The capability needs filesystem or process access on the user's machine, or the data must not leave the deviceMany clients need it concurrently, or it must be centrally patched
MCP server, remote (Streamable HTTP)Many hosts share one capability, and you need central auth, audit and versioningThe data is local-only, or the latency budget cannot absorb a network hop per call
MCP connector on the Messages APIYou want a remote MCP server attached to API calls without writing an MCP client yourselfYou need MCP prompts or resources, because the connector is tools-only, or the server is stdio
Agent-to-agent or subagent delegationThe remote unit is opaque, reasons over multiple steps, has its own context window, and returns a condensed resultThe remote unit is a plain schema-shaped function call
Plain RAG (retrieve then answer)Read-only grounded question answering over a corpus, citations required, no actions takenThe task requires acting, the corpus fits in context, or freshness is measured in seconds
Two of these are not integrations at all. Subagent delegation and plain RAG are in the same table because scenarios offer them as options against the other four. The tell for delegation is that the far end reasons; the tell for RAG is that nothing is written.

2.1Four anti-patterns to recognise on sight

These are not subtle mistakes. They are the shapes that recur in distractors, and each one has a stated right answer behind it.

Named anti-patterns and what to do instead
Anti-patternWhy it failsInstead
Wrapping every REST endpoint as a toolAnthropic's guidance is explicit: build for high-impact workflows, not API parity. Endpoint-shaped tools push orchestration into the model and burn context on definitions nobody callsOne schedule_event beats list_users plus list_events plus create_event
Using MCP as an inter-service RPC layer between backends you ownMCP is a context protocol for model-facing capability, not a service mesh. You pay protocol overhead for no model-facing benefitCall the service directly. Reserve MCP for capability a model consumes
Using an agent where a workflow sufficesWorkflows orchestrate models through predefined code paths; agents let the model direct its own process. Agents cost more, need sandboxing, and compound errorsOrder of preference: single call, then workflow, then agent
Standing up a vector database for a small corpusUnder roughly 200k tokens there is nothing for retrieval to win, and you have added a whole failure modeInline the corpus and use prompt caching. Section 6 has the numbers
Watch out

"Expose all endpoints as tools for full capability" reads like thoroughness and is directly contradicted by the guidance. Any option whose justification is completeness of coverage rather than a workflow the user actually performs is the wrong option.

An insurer wants a policy-lookup capability available three ways: in Claude Desktop for the claims team, inside two internal web applications, and from a nightly batch job. Security has said there must be one place to rotate the backing credential and one audit log covering every lookup. The claims team also wants a set of pre-written claim-summary templates available to them as slash commands. Policy data already lives in a central service with a 40 ms API.

Which integration mechanism fits?

  1. A local stdio MCP server installed on each analyst's machine
  2. A remote MCP server over Streamable HTTP, with each host running its own MCP client
  3. The MCP connector on the Messages API, pointed at a remote server
  4. Direct SDK tool use, implemented separately in each of the three applications
Templates as slash commands means prompts, and prompts mean a real MCP client. Central credential rotation and one audit log already rule out local and per-application integrations. The only line that separates B from C is the request for templates, because MCP prompts are a primitive the Messages API connector does not carry.

When you cannot tell two mechanisms apart, say out loud who else consumes the capability and what is not permitted to move. Those two sentences have decided it in every scenario worth asking about.
