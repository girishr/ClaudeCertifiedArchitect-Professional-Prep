Failure modes and mitigations

Nine ways these systems fail, the control for each, and the fix that sounds right and is not.

Items in this part of the domain describe a symptom and offer four remedies. Usually three of them are real techniques that would help with something else, and one of them is the thing that addresses the mechanism. So learn the table by its right-hand column: the tempting fix is what you have to recognise fast, because it is what the item is built around.

4.1The four that are really one problem

Indirect injection, exfiltration, over-permissioning and confused deputy are the same architectural mistake seen from four angles: something crossed a boundary that should have held. None of them is fixed by changing what the model is told, because in all four cases the model behaved exactly as instructed by whoever got to it last.

Two moves cover most of this territory. Untrusted third-party content goes into a tool result block, JSON-encoded, with its origin declared, and gets screened by a cheap classifier before the model acts on it. And the tool call carries the caller's identity and permissions, not the agent's, so an agent that can read ten systems cannot lend that reach to a user who can read one.

Watch out

Exfiltration is a scope-and-egress problem, not an output-filtering problem. By the time a response is being filtered, the tool call that sent the data out has already returned. Separate the read scope from the egress path and allow-list the destinations.

4.2The two that are about honesty

Hallucination and non-determinism are not attacks. They are properties, and the failure is in what you promised about them. A bigger model reduces the hallucination rate and never removes it, so the control is grounding plus validation plus an eval that measures groundedness, along with a design that permits "I don't know" as a valid output.

Non-determinism is the same shape. You do not make the system deterministic. You pin model versions, hold a regression eval suite in CI, use structured outputs, and canary any rollout, so that variance shows up in your tests rather than in a customer's quarter. And you never commit to deterministic behaviour in a contract.

Both branches of the undo rule. The kill switch and the rollback to a previous prompt or model version are the same instinct as the human gate: the question is never only "will this go wrong" but "what gets us back when it does".

When you see a symptom, name the boundary that failed before you pick a remedy. If the answer you like is about wording, and the failure was about reach, you have the wrong answer.
