The layered guardrail stack

Five layers, what each one cannot do, and how much of the stack the stated risk actually pays for.

Exam domain 5From this kit's domain notes
CCAR-P course / Module 3 / Section 02 of 8

You are shown a design and asked which controls it needs. The wrong instinct is to add everything, because the list is finite and each item sounds responsible. The stack is not a checklist you complete. It is five layers that catch different failure classes at different prices, and the examinable knowledge is what each one cannot do.

The mechanism at each layer, and its blind spot
LayerMechanismCatchesMisses
Input filtering Regex and deny-lists, PII redaction, a cheap classifier (Haiku-class) screening the user turn Known-pattern injection, obvious abuse, PII entering the boundary at all Novel phrasing. Indirect injection arriving later via tools
Prompt-level constraints System prompt scope, refusal instructions, declaring untrusted content as untrusted, role boundaries Drift, scope creep, casual misuse Determined adversaries. Never a security boundary on its own
Tool permissioning Least-privilege scopes, read-only defaults, allow / approve / block per action, sandboxing, egress restriction Exfiltration, confused deputy, over-broad blast radius Anything within the granted scope
Output validation Schema and structured-output enforcement, groundedness and citation checks, a safety classifier on the response, business-rule assertions Hallucinated facts and fields, unsafe content, malformed handoffs to downstream systems Plausible-but-wrong content that passes every rule
Post-hoc monitoring Logging, sampled human review, drift and refusal-rate dashboards, incident alerting, red-team cadence Slow-moving degradation, novel attacks, aggregate bias Nothing in real time. It is detection, not prevention
What each layer costs, and what makes you reach for it
LayerCostReach for it when
Input filteringLow latency, low costAlways for PII. Beyond that, when abuse volume is high enough to justify pre-screening
Prompt-level constraintsFreeAlways, but never as the only control
Tool permissioningDesign cost, some frictionAny agent with write access or network reach
Output validationAdds a model call and latencyWhen the output is consumed by a system or shown to a customer
Post-hoc monitoringOngoing operational costAlways. This is the layer teams skip and the exam punishes

2.1Proportionality

Control cost should track expected loss, meaning severity multiplied by likelihood. It should not track the loudest stakeholder's anxiety, and it should not track how sophisticated the stack looks in a slide.

So maximum control is a wrong answer, not a safe one, when the stem gives you a low-severity, reversible, internal use case and mentions latency or cost pressure. The correct stack there is prompt constraints plus logging plus sampled review, and nothing else yet. The phrase "nothing else yet" is doing real work: you are not refusing the other layers, you are refusing to pay for them before the risk earns them.

The cheap half comes first. Prompt constraints are free and monitoring is the layer that tells you which of the expensive layers you actually need. Starting there is not cutting corners, it is how you find out where the money should go.

2.2Defence in depth is about independence, not count

Two layers that fail for the same reason are one layer. A prompt instruction and a model-based refusal are correlated: both are the model deciding to behave, and both give way to the same pressure. A prompt instruction and a hard tool-permission boundary are not correlated, because the second one holds whatever the model decides.

This is also why the stack is ordered the way it is. Input filtering and prompt constraints shape intent. Tool permissioning caps consequence. Output validation checks the result. Monitoring is the only one that operates after the fact, which is exactly why it is the layer that finds the attack nobody designed for.

Watch out

"Strengthen the system prompt" offered against a security problem is almost always the distractor. It is free, it sounds diligent, and it is correlated with the control that already failed. If the threat is injection, exfiltration or an over-broad agent, the answer lives in tool scope and sandboxing.

Price the stack against the harm, and put the independent boundary where the consequence is. A design where the cheapest layer is the only thing standing between the model and an irreversible action has no depth at all, however many controls are on the diagram.
